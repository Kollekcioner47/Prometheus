Практика 7. Экспортёры в контейнерах и Docker.

ЭТА ПРАКТИКА — ПРО КОНТЕЙНЕРЫ. Мы поставим Docker на app1,
разберёмся, что меняется в мониторинге, когда сервис живёт

ЧТО МЫ СДЕЛАЕМ
=========================================================================

Поставим Docker Engine из репозитория download.docker.com и убедимся,

с целью 10.0.2.13:8080 и разберём ключевые метрики контейнеров:

container_network_receive_bytes_total, container_fs_usage_bytes —

Создадим нагрузку: поднимем nginx и redis в контейнерах и посмотрим,
как цифры на графике соотносятся с выводом docker stats.

Разберём второй подход к сбору метрик о контейнерах — docker_exporter —
и объясним, почему основным в курсе остаётся cAdvisor. Включим метрики
самого демона Docker и честно скажем, что означает монтирование
/var/run/docker.sock в контейнер.

Соберём полный стек мониторинга в docker compose: Prometheus, Grafana,
node_exporter и cAdvisor. Разберём файл по блокам, запустим его
на app1 и увидим, почему Grafana в этом стеке публикуется на 3001,
а не на 3000.

В конце сравним два способа запускать мониторинг — службы systemd
и контейнеры — и скажем, что выбирают в работе.

=========================================================================
ШАГ 1. ЧТО МЕНЯЕТСЯ, КОГДА СЕРВИС ЖИВЁТ В КОНТЕЙНЕРЕ
=========================================================================

КОНТЕЙНЕР (container) — это процесс, которому ядро Linux ограничило
видимость: своё дерево файлов, своя таблица процессов, свой сетевой
стек, свои пределы по процессору и памяти. Ядро при этом общее
с остальной машиной.

Отсюда первое следствие для мониторинга, и оно главное в этой практике:
у контейнера нет своего ядра и нет своей машины. Всё, что мы измеряли
до сих пор, измерялось на уровне операционной системы целиком.
node_exporter на app1 отвечает на вопрос «сколько процессора занято
на машине», и ответ будет одинаковым независимо от того, живут
в контейнерах nginx и redis или работают службами.

Чего node_exporter сказать не может:

  * сколько процессора занял конкретный контейнер;
  * сколько памяти он держит в рабочем наборе;
  * сколько он прочитал из сети;
  * какой образ и какая версия этого образа запущены;
  * сколько контейнеров вообще работает на машине прямо сейчас.

Всё это известно ядру и демону Docker, но не видно как метрики.
Пробел заполняет cAdvisor.

ВАЖНО: cAdvisor читает данные не изнутри контейнеров, а снаружи —
из cgroup и из API демона Docker на самой машине. Поэтому он не требует
ничего устанавливать внутрь отслеживаемых контейнеров, но ему нужны
широкие права на хосте. Как именно это устроено, разберём в шаге 4.

ВТОРОЕ СЛЕДСТВИЕ: приложение внутри контейнера отдаёт свои метрики
тем же способом, что и раньше. nginx в контейнере по-прежнему может
отдавать stub_status, а nginx-prometheus-exporter по-прежнему может
его читать. Метрики о контейнере и метрики о приложении внутри него —
два разных набора, и нужны оба. Первый отвечает «сколько ресурсов
съел контейнер», второй — «что происходило внутри приложения».

ПОЧЕМУ ИМЕННО ТАК: сбор метрик контейнеров вынесен в отдельный
процесс, а не встроен в сам Docker. Демон Docker занят своей работой,
и его метрики — это в первую очередь метрики демона, а не контейнеров.
К тому же cAdvisor умеет читать не только Docker: тот же набор
container_* метрик он отдаёт и для кластера Kubernetes, и для других
средств запуска контейнеров. Именно поэтому в курсе разбирается он:
метрики те же, что отдают контейнеры в кластере.

ЗАЧЕМ ЭТО В РАБОТЕ: вопрос «кто съел память на узле» в контейнерной
среде задаётся постоянно, а ответ на него есть ровно в двух местах —
в cgroup и в метриках контейнеров. Без них остаётся только заходить
на машину и смотреть docker stats, а это не масштабируется даже
на десять узлов.


=========================================================================
ШАГ 2. DOCKER НА APP1
=========================================================================

Заходим на app1 под учётной записью engineer:

  ssh engineer@10.0.2.13

Docker Engine в курсе ставится из официального репозитория
download.docker.com. Из репозитория Ubuntu его ставить не нужно:
пакет docker.io в Ubuntu 26.04 отстаёт от текущей версии, а нам нужна
и сама версия, и плагин docker compose, который идёт тем же пакетом.

Сначала уберём то, что может помешать:

  sudo apt remove -y docker.io docker-compose docker-doc podman-docker \
      containerd runc

На чистой Ubuntu 26.04 эта команда ничего не удалит и ответит
«Package 'docker.io' is not installed, so not removed». Это нормальный
результат, а не ошибка.

Ставим зависимости и подключаем репозиторий:

  sudo apt update
  sudo apt install -y ca-certificates curl
  sudo install -m 0755 -d /etc/apt/keyrings
  sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
      -o /etc/apt/keyrings/docker.asc
  sudo chmod a+r /etc/apt/keyrings/docker.asc

  sudo printf 'deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu %s stable\n' "$(. /etc/os-release && echo $VERSION_CODENAME)" | sudo tee /etc/apt/sources.list.d/docker.list

Ставим сам движок и плагин compose:

  sudo apt update
  sudo apt install -y docker-ce docker-ce-cli containerd.io \
      docker-buildx-plugin docker-compose-plugin

Проверяем:

  docker --version
  Docker version 28.5.1, build 1234abc

  sudo systemctl status docker --no-pager | head -5
  ● docker.service - Docker Application Container Engine
       Loaded: loaded (/usr/lib/systemd/system/docker.service; enabled)
       Active: active (running) since ...

Версия в выводе зависит от того, когда вы обновляли репозиторий,
и может отличаться от приведённой. Важно, что команда отвечает
и служба запущена.

Теперь про учётную запись. По умолчанию docker доступен только root:
сокет /var/run/docker.sock принадлежит root и группе docker, а engineer
в неё не входит. Добавим:

  sudo usermod -aG docker engineer

ВАЖНО: членство в группе проверяется при входе в систему. Уже открытая
сессия останется без новых прав, и следующая команда всё равно ответит
отказом. Нужно выйти и зайти снова, либо применить группу к текущей
оболочке:

  newgrp docker

Проверяем, что права применились, и запускаем первый контейнер:

  id
  uid=1000(engineer) gid=1000(engineer) groups=1000(engineer),27(sudo),988(docker)

  docker run --rm hello-world
  Unable to find image 'hello-world:latest' locally
  latest: Pulling from library/hello-world
  ...
  Hello from Docker!
  This message shows that your installation appears to be working correctly.

ПРОБЛЕМА В ЭТОЙ КОМАНДЕ ЕСТЬ, и о ней нужно сказать прямо. Тег latest
здесь используется, хотя в курсе он запрещён. Причина в том, что это
официальная проверочная команда из документации Docker: она нужна
ровно один раз, чтобы убедиться, что установка работает, и никакого
отношения к учебному стенду не имеет. В собственных файлах —
в docker run для своих сервисов и в docker compose — тег latest
не используется нигде. Версия — это ответ на вопрос «что у меня
установлено», и спрашивают его первым, когда что-то сломалось.

ЧЕГО НЕ ДЕЛАТЬ: не работайте с Docker от root и не запускайте
sudo docker ... по привычке. Демон и так работает от root, а через
группу docker вы получаете доступ к нему без sudo. Разница
принципиальная: sudo docker не оставляет следов в правах, а группа
docker — это постоянный доступ, и он опасен (об этом в шаге 7).
Правильный порядок — добавить себя в группу один раз.

ПРОВЕРКА: команда docker info выполняется без sudo и в разделе Server
показывает версию движка:

  docker info --format '{{ .ServerVersion }}'
  28.5.1


=========================================================================
ШАГ 3. КОНТЕЙНЕРЫ ДЛЯ НАГЛЯДНОСТИ
=========================================================================

Прежде чем ставить cAdvisor, запустим два контейнера, на которых будет
видна нагрузка. Пустой стенд даёт пустые графики, и по ним ничего
не понять.

nginx:

  docker run -d --name web-lab --restart unless-stopped \
      -p 8080:80 nginx:1.29.0

redis:

  docker run -d --name cache-lab --restart unless-stopped \
      redis:8.2.1

Оба образа — конкретных версий, без latest. Версии взяты на момент
подготовки курса; если в реестре уже другие, номер подставляется
в команду, а принцип остаётся тот же.

Проверяем:

  docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
  NAMES       IMAGE          STATUS
  cache-lab   redis:8.2.1    Up 5 seconds
  web-lab     nginx:1.29.0   Up 6 seconds

Обратите внимание на порт: nginx в контейнере опубликован на 8080,
а порт 8080 на app1 нужен cAdvisor. На web1 порт 8080 не занят ничем,
но это не помогает: там работают nginx-prometheus-exporter на 9113
и stub_status на 8081, и они к app1 отношения не имеют. Порты реестра
подобраны так, чтобы в одной практике они не сталкивались, — и 8080
остаётся за cAdvisor. Поэтому публикацию порта у nginx убираем:

  docker stop web-lab && docker rm web-lab

Вместо публикации порта наружу nginx будет доступен только внутри
docker-сети, и этого достаточно: нам нужен он сам, его процессор
и его память, а не его страница в браузере.

  docker run -d --name web-lab --restart unless-stopped nginx:1.29.0

  docker ps --format 'table {{.Names}}\t{{.Status}}'
  NAMES       STATUS
  cache-lab   Up About a minute
  web-lab     Up 3 seconds

ПОЧЕМУ ИМЕННО ТАК: имя контейнера задано явно (web-lab, cache-lab).
Без --name Docker выдаёт случайные имена вида dreamy_morse, и тогда
метка name в метриках меняется при каждом пересоздании контейнера.
Для графика это означает, что ряд не продолжается, а начинается заново
с новым именем, — и история теряется именно тогда, когда она нужна.

ЗАЧЕМ ЭТО В РАБОТЕ: имена контейнеров и метка name — часть контракта
с мониторингом. Если контейнер пересоздаётся системой развёртывания
с новым именем, графики придётся читать по метке image, а не name.
Поэтому в рабочей среде имена стараются делать предсказуемыми.


=========================================================================
ШАГ 4. CADVISOR: ЗАПУСК И РАЗБОР ФЛАГОВ
=========================================================================

cAdvisor (Container Advisor) — экспортёр метрик контейнеров. Он читает
cgroup, которые ведёт ядро, и дополняет их сведениями из API демона
Docker. Формат вывода — тот же exposition, что у node_exporter.

Запускается он контейнером. Другого способа в курсе нет: cAdvisor
распространяется в первую очередь как образ, а собрать его из исходников
означало бы поставить на стенд Go и разбираться со сборкой — это
отдельная тема и к мониторингу отношения не имеет.

Команда запуска целиком, одной строкой (она же лежит в
files/07_containers/run_cadvisor.txt вместе с разбором каждого флага):

  docker run -d --name cadvisor --restart unless-stopped --privileged --publish 8080:8080 --volume /:/rootfs:ro --volume /var/run:/var/run:ro --volume /sys:/sys:ro --volume /var/lib/docker/:/var/lib/docker:ro --volume /dev/disk/:/dev/disk:ro --volume /var/run/docker.sock:/var/run/docker.sock:ro --device /dev/kmsg gcr.io/cadvisor/cadvisor:v0.55.1

Разберём флаги по группам, потому что без понимания томов cAdvisor
превращается в чёрный ящик.

  --privileged        контейнер получает доступ ко всем устройствам
                      хоста и теряет ограничения по возможностям ядра.
  --publish 8080:8080 порт 8080 машины app1 передаётся в порт 8080
                      контейнера. Это порт cAdvisor из реестра курса.
  --volume /:/rootfs:ro
                      корень хоста виден контейнеру как /rootfs, только
                      для чтения.
  --volume /var/run:/var/run:ro
                      каталог /var/run целиком: там сведения о процессах.
  --volume /sys:/sys:ro
                      cgroup и статистика устройств ядра.
  --volume /var/lib/docker/:/var/lib/docker:ro
                      данные Docker: слои образов и метаданные.
  --volume /dev/disk/:/dev/disk:ro
                      ссылки на диски: по ним считаются метрики ввода-вывода.
  --volume /var/run/docker.sock:/var/run/docker.sock:ro
                      сокет демона Docker: имена, образы и идентификаторы
                      контейнеров.
  --device /dev/kmsg   доступ к буферу сообщений ядра.

ПОЧЕМУ ИМЕННО ТАК: про режим ro у томов. Слово ro (read-only)
обозначает запрет менять файлы и каталоги этого тома. Для /sys,
/var/lib/docker и корня машины это ровно то, что нужно: cAdvisor
только читает. Но у сокета Docker режим ro означает другое:
запрещено менять сам файл сокета, а разговаривать через него — можно.
Сокет двусторонний: процесс в контейнере отправляет демону команды
и получает ответы. Подробно об этом в шаге 7.

ВАЖНО: если запустить cAdvisor без тома /sys, контейнер не переживёт
старт. Он читает /sys/fs/cgroup и падает, если каталога нет. Состояние
Restarting в docker ps при живом образе — чаще всего именно эта ошибка,
а не «сломанный cAdvisor».

Проверяем, что cAdvisor отвечает:

  curl -s http://localhost:8080/healthz
  ok

  curl -s http://localhost:8080/metrics | grep -c '^container_'
  1840

Число строк container_* зависит от числа контейнеров на машине,
поэтому в курсе приводится порядок величины. Если у вас получилось
1200 или 2500 — это не ошибка.

ПРОВЕРКА: команда docker ps показывает cadvisor в состоянии Up,
а не Restarting:

  docker ps --filter name=cadvisor --format '{{.Names}} {{.Status}}'
  cadvisor Up 40 seconds


=========================================================================
ШАГ 5. ЗАДАНИЕ DOCKER В PROMETHEUS
=========================================================================

cAdvisor отдаёт метрики, но Prometheus о нём пока не знает. Добавим
задание. Работаем на mon, в файле /etc/prometheus/prometheus.yml.

Фрагмент целиком лежит в files/07_containers/prometheus.fragment.yml.
Ниже он напечатан; в рабочую конфигурацию из него добавляется только
задание docker (и, если его ещё нет, ключ rule_files — он понадобится
в практике 8):

  # files/07_containers/prometheus.fragment.yml
  #
  # Практика 7, шаг 5. Это фрагмент, а не полный конфигурационный файл:
  # Prometheus с ним не запустится. Он показывает, как выглядит рабочая
  # конфигурация Prometheus на машине mon после добавления задания docker.
  #
  # Задание дописывается в секцию scrape_configs файла
  # /etc/prometheus/prometheus.yml. Перед перезагрузкой конфигурации:
  #
  #   promtool check config /etc/prometheus/prometheus.yml
  #
  # Внешние метки берутся из реестра сущностей курса: env=lab,
  # host=имя хоста, monitor=prometheus-01.

  global:
    scrape_interval: 15s
    evaluation_interval: 15s
    external_labels:
      env: lab
      host: mon
      monitor: prometheus-01

  rule_files:
    - /etc/prometheus/rules/*.yml

  storage:
    tsdb:
      retention:
        time: 15d

  scrape_configs:

    # Метрики самого Prometheus. Без метки env: это единственное задание,
    # у которого её нет, — так заведено в реестре сущностей курса.
    - job_name: prometheus
      static_configs:
        - targets:
            - localhost:9090

    # Машины стенда: node_exporter из практики 2.
    - job_name: node
      static_configs:
        - targets:
            - 10.0.2.5:9100
            - 10.0.2.11:9100
            - 10.0.2.12:9100
            - 10.0.2.13:9100
          labels:
            env: lab

    # Контейнеры на app1: cAdvisor слушает порт 8080.
    # Метка instance у цели станет 10.0.2.13:8080, метка job — docker.
    # Никаких дополнительных меток не нужно: cAdvisor отдаёт метки
    # name, image и id в самих метриках, и перемаркировка здесь была бы
    # лишним шагом (она разбирается в практике 11).
    - job_name: docker
      static_configs:
        - targets:
            - 10.0.2.13:8080
          labels:
            env: lab

Проверяем конфигурацию и перезагружаем:

  promtool check config /etc/prometheus/prometheus.yml
  SUCCESS: /etc/prometheus/prometheus.yml is valid prometheus config file syntax

  curl -X POST http://localhost:9090/-/reload

Смотрим на страницу Targets (http://10.0.2.5:9090/targets):

  docker  10.0.2.13:8080  UP  ...  env="lab", instance="10.0.2.13:8080", job="docker"

ПОЧЕМУ ИМЕННО ТАК: одно задание docker на одну машину с cAdvisor,
а не отдельное задание на контейнер. Задание — это единица сбора,
а не единица наблюдения: одному cAdvisor соответствует одна цель,
и все контейнеры приходят из неё. Разделять их на задания пришлось бы
только в одном случае — если бы у разных групп контейнеров были разные
интервалы сбора или разные правила перемаркировки. Такой случай
разбирается в практике 11.

ПРОВЕРКА: запрос в веб-интерфейсе Prometheus на вкладке Graph:

  count(container_last_seen{job="docker"})

Число должно быть не меньше числа работающих контейнеров. У нас
на app1 работают web-lab, cache-lab и сам cadvisor — то есть минимум
три. Если результат пустой, смотрим состояние цели на странице Targets
и текст ошибки в колонке Error.


=========================================================================
ШАГ 6. КЛЮЧЕВЫЕ МЕТРИКИ КОНТЕЙНЕРОВ
=========================================================================

Откроем список метрик и посмотрим, что вообще отдаёт cAdvisor. Метрик
много — сотни — и запоминать их все не нужно. Нужно понимать, как они
устроены: имя, единица измерения и метки.

  curl -s http://10.0.2.13:8080/metrics | grep '^# HELP container_cpu' | head -3

Четыре метрики, которые используются в работе постоянно:

  container_cpu_usage_seconds_total
    Счётчик: сколько секунд процессорного времени израсходовал
    контейнер за всё время жизни. Так же, как node_cpu_seconds_total,
    он только растёт, поэтому напрямую его читать бессмысленно:
    нужен rate.

  container_memory_working_set_bytes
    Показатель (gauge): объём памяти, который контейнер реально
    занимает в данный момент и который нельзя вытеснить без
    последствий. Это то число, которое показывает docker stats
    в колонке MEM USAGE.

  container_network_receive_bytes_total
    Счётчик: сколько байт контейнер принял через сетевые интерфейсы.
    Есть и парная метрика container_network_transmit_bytes_total.

  container_fs_usage_bytes
    Показатель: сколько занимает файловая система контейнера —
    слои образа плюс то, что записано сверху.

Запросы к ним выглядят привычно. Загрузка процессора по контейнерам
за последние пять минут:

  sum by (name) (
    rate(container_cpu_usage_seconds_total{job="docker", name!=""}[5m])
  )

Память в мегабайтах:

  sum by (name) (
    container_memory_working_set_bytes{job="docker", name!=""}
  ) / 1024 / 1024

Скорость приёма по сети:

  sum by (name) (
    rate(container_network_receive_bytes_total{job="docker", name!=""}[5m])
  )

Метки у этих метрик — самое важное в шаге:

  name     имя контейнера, например web-lab;
  image    имя образа, например nginx:1.29.0;
  id       полный идентификатор контейнера;
  job      всегда docker: его добавляет Prometheus из имени задания;
  instance 10.0.2.13:8080 — адрес cAdvisor, а не адрес контейнера.

ВАЖНО: фильтр name!="" в запросах не украшение. cAdvisor отдаёт часть
рядов с пустым именем — это сводные показатели по всей машине
и по родительским cgroup. Без фильтра sum by (name) покажет лишнюю
строку с пустым именем, значение которой больше, чем у всех контейнеров
вместе, и первый же вопрос на разборе будет «почему nginx съел
шесть гигабайт».

ПОЧЕМУ ИМЕННО ТАК: instance у метрик контейнера — это адрес cAdvisor,
а не контейнера. Так устроена pull-модель: Prometheus собирает метрики
с того адреса, который указан в цели, и подставляет его в метку
instance. Адреса у контейнеров в метрике нет и быть не может: у них
нет собственного адреса, видимого Prometheus.

ЧЕГО НЕ ДЕЛАТЬ: не пытайтесь различать контейнеры по метке id.
Идентификатор меняется при каждом пересоздании контейнера, и график
при обновлении образа разорвётся. id годится для того, чтобы найти
контейнер командой docker inspect, но не для группировки на графике.


=========================================================================
ШАГ 7. НАГРУЗКА И СРАВНЕНИЕ С DOCKER STATS
=========================================================================

Пустые контейнеры почти ничего не потребляют, и на графике это выглядит
как ровная линия у нуля. Создадим нагрузку — и не «вообще», а такую,
чтобы её было видно и в Prometheus, и в docker stats.

Нагрузка на процессор. Запускаем в контейнере web-lab бесконечный
цикл в четырёх процессах:

  docker exec -d web-lab sh -c 'for i in 1 2 3 4; do while :; do :; done & done'

Нагрузка на сеть. Создаём трафик к контейнеру web-lab снаружи,
контейнером с curl. Утилита curl берётся из отдельного образа,
и версия у него тоже закреплена:

  for i in $(seq 1 20); do
    docker run --rm curlimages/curl:8.16.0 \
        -s -o /dev/null http://10.0.2.13:8080/healthz
  done

Альтернатива, если не хочется запускать двадцать контейнеров: сделать
то же самое одним контейнером с циклом внутри, передав ему команду:

  docker run --rm curlimages/curl:8.16.0 sh -c \
      'i=0; while [ $i -lt 200 ]; do curl -s -o /dev/null http://10.0.2.13:8080/healthz; i=$((i+1)); done'

Обратите внимание, куда идёт трафик: на порт 8080 машины, то есть
в контейнер cAdvisor. Для нагрузки это подходит так же, как обращение
к nginx, — сети всё равно, чей это порт. Метрики эту нагрузку увидят
на двух контейнерах сразу: у cAdvisor она попадёт в приём,
у контейнера с curl — в передачу. Именно это и интересно: одна
и та же передача данных видна с двух сторон, и значения не совпадут
в точности. Учёт ведётся по интерфейсам, а служебный трафик
и повторные попытки попадают в разные стороны по-разному.

ЧЕГО НЕ ДЕЛАТЬ: не создавайте нагрузку на боевом стенде «чтобы
посмотреть». Все команды этого шага запускаются только на учебной
машине app1, и после них нагрузку нужно снять. Здесь это сделано
двумя способами: цикл в контейнере заканчивается сам, а процессорную
нагрузку снимаем отдельной командой ниже.

Теперь смотрим на цифры с двух сторон. Сначала docker stats:

  docker stats --no-stream
  CONTAINER ID   NAME        CPU %     MEM USAGE / LIMIT   MEM %   NET I/O
  1a2b3c4d5e6f   web-lab     398.5%    12.5MiB / 3.8GiB    0.32%   1.2kB / 648B
  6f5e4d3c2b1a   cache-lab   0.1%      7.1MiB / 3.8GiB     0.18%   14.5kB / 3.1kB
  ...

CPU 398.5% означает, что контейнер занял примерно четыре ядра:
сто процентов — это одно ядро целиком. На четырёхъядерной машине
такое значение не должно удивлять.

Ту же картину видно в Prometheus. Запрос из предыдущего шага:

  sum by (name) (
    rate(container_cpu_usage_seconds_total{job="docker", name!=""}[5m])
  )

Одна тонкость: этот запрос вернёт не проценты, а доли. 3.98 в ответе
означает те же 398 %, что и в docker stats. Чтобы получить проценты,
умножьте на 100.

Дальше есть смысл поставить два окна рядом: docker stats в терминале
и график Prometheus в браузере. Значения совпадут, но не мгновенно:
Prometheus собирает метрики раз в 15 секунд, а docker stats читает
cgroup в момент запроса. Пятиминутное окно rate размазывает изменения
ещё сильнее, поэтому график будет плавнее и придёт к тому же значению
на несколько секунд позже. Это не ошибка, а свойство модели сбора.

ПРОВЕРКА: память контейнера web-lab по версии Prometheus совпадает
с колонкой MEM USAGE из docker stats в пределах нескольких процентов:

  container_memory_working_set_bytes{job="docker", name="web-lab"} / 1024 / 1024

Уберём нагрузку, чтобы машина не грелась:

  docker exec web-lab sh -c 'kill -9 -1'


=========================================================================
ШАГ 8. МЕТРИКИ ДЕМОНА DOCKER И САМЫЙ ЧЕСТНЫЙ РАЗГОВОР О СОКЕТЕ
=========================================================================

cAdvisor рассказывает о контейнерах. Про сам демон Docker он не знает
почти ничего: сколько образов лежит на машине, сколько места занимают
слои, какие ошибки демон считает — это его собственная статистика.

У демона есть встроенная отдача метрик на HTTP-порт. Включается она
в файле /etc/docker/daemon.json:

  sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
  {
    "metrics-addr": "127.0.0.1:9323",
    "experimental": true
  }
  EOF
  sudo systemctl restart docker

Проверяем:

  curl -s http://127.0.0.1:9323/metrics | grep '^# HELP engine_' | head -3
  # HELP engine_daemon_container_actions_seconds The number of seconds it takes to process each container action
  # HELP engine_daemon_container_states_containers The count of containers in various states
  ...

Что здесь важно понимать. Адрес 127.0.0.1, а не 0.0.0.0: метрики демона
содержат сведения о внутреннем устройстве Docker, и открывать их
в сеть без аутентификации не нужно. Если они понадобились Prometheus
на другой машине, правильный путь — не публиковать порт наружу,
а поставить перед ним обратный прокси с аутентификацией или собирать
их локально. В курсе мы оставляем 127.0.0.1 и разбираем метрики
на месте.

Флаг experimental нужен потому, что часть метрик демона до сих пор
помечена как экспериментальная. Честная оговорка: набор engine_*
метрик меняется от версии к версии, и полагаться на конкретные имена
в правилах оповещения не стоит.

Теперь самый важный разговор практики — про /var/run/docker.sock.

Сокет Docker — это точка управления демоном. Демон работает от root
и по этому сокету принимает команды: создать контейнер, смонтировать
каталог, выполнить команду. Никакой аутентификации внутри сокета нет:
право разговаривать с ним определяется правами на файл сокета. Кто
может в него писать, тот может от имени демона запустить контейнер
с любыми томами — а значит, получить доступ ко всей файловой системе
машины. В документации Docker это описано прямо: доступ к сокету
равносилен доступу root на хосте.

ЧТО ЭТО ЗНАЧИТ ДЛЯ НАС, по пунктам:

  * cAdvisor получает сокет. Значит, контейнер cAdvisor — доверенный.
    Его образ должен быть из проверенного источника и закреплён
    по версии; обновлять его нужно осознанно, а не «когда захочется».
  * Режим ro у сокета не защищает. Он запрещает менять файл сокета,
    но сокет двусторонний, и разговаривать через него контейнер может
    полноценно.
  * Контейнер cAdvisor запущен с --privileged. Это ещё шире: он видит
    устройства хоста и не ограничен возможностями ядра. Такой контейнер
    не должен быть доступен по сети никому, кроме администратора.
  * Если на машине работают чужие контейнеры, запускать рядом cAdvisor
    с сокетом — решение, которое нужно принимать осознанно. Пользователь,
    который может пересоздать контейнер cAdvisor с другим образом,
    получает root на машине.

ЧЕГО НЕ ДЕЛАТЬ: не монтируйте docker.sock в контейнеры приложений
«чтобы было удобно». Типовая ошибка — контейнер со сборочным агентом
или с панелью управления, которому «нужно видеть контейнеры»:
он получает сокет, а вместе с ним и root на хосте. Если очень нужно
управлять контейнерами из контейнера, для этого существуют отдельные
механизмы с ограничением прав, и разбираются они не в курсе
про мониторинг, а в курсе про контейнеры.

ПОЧЕМУ ИМЕННО ТАК, и почему мы всё равно это делаем: без сокета
cAdvisor не сможет получить список контейнеров и их метки name и image.
Он отдаст метрики по cgroup — с идентификаторами, но без имён, и по
графикам нельзя будет понять, какой ряд какому сервису соответствует.
Выбор здесь не между «безопасно» и «небезопасно», а между «есть метки»
и «нет меток». Мы выбираем метки и говорим вслух, чем за это платим.

ЗАЧЕМ ЭТО В РАБОТЕ: правило «сокет Docker — это root» стоит помнить
не только про cAdvisor. Оно объясняет, почему доступ к сборочным
серверам и к узлам с контейнерами ограничивают так же строго, как
доступ к root.


=========================================================================
ШАГ 9. ВТОРОЙ ПОДХОД: DOCKER_EXPORTER, И ПОЧЕМУ ОСНОВНОЙ — CADVISOR
=========================================================================

cAdvisor — не единственный способ получить метрики о контейнерах.
Есть отдельные экспортёры, которые сами опрашивают API Docker и отдают
Prometheus небольшой набор метрик. Один из них так и называется —
docker_exporter (у него нет отношения к официальному проекту Docker;
это сторонняя разработка, и в курсе он разбирается обзорно).

Он запускается так же контейнером, но получает только сокет Docker —
без /sys, без cgroups, без --privileged:

  docker run -d --name docker-exporter --restart unless-stopped \
      -p 9417:9417 -v /var/run/docker.sock:/var/run/docker.sock:ro \
      prometheusnet/docker_exporter:v1.8.0

Разница в подходе принципиальная. cAdvisor измеряет: он читает cgroup,
то есть цифры фактического потребления ресурсов, которые ведёт ядро.
docker_exporter описывает: он спрашивает у демона список контейнеров,
их состояние, число запущенных, размер образа. Метрик потребления
процессора и памяти в нём либо нет, либо они берутся из тех же cgroup
другим способом.

Практическое следствие: docker_exporter хорош для ответа на вопрос
«сколько контейнеров запущено и в каком они состоянии», и не годится
для вопроса «сколько ресурсов занял сервис».

Сравним по пунктам:

  cAdvisor
    * метрики потребления из cgroup: процессор, память, сеть, диск;
    * те же имена метрик, что в Kubernetes;
    * требует --privileged и монтирования /sys, /var/lib/docker;
    * тяжёлый: сотни метрик на каждый контейнер, заметная нагрузка;
    * один на машину.

  docker_exporter
    * состояние контейнеров и метаданные из API Docker;
    * метрик потребления почти нет;
    * требует только сокет;
    * лёгкий: десятки метрик;
    * может запускаться и рядом с cAdvisor, если нужны метаданные.

ПОЧЕМУ ИМЕННО ТАК, почему в курсе основной cAdvisor:

  * метрики потребления нужны чаще, чем метаданные. Вопрос «кто съел
    память» задаётся в сто раз чаще, чем «сколько всего контейнеров»;
  * имена метрик совпадают с теми, что отдают контейнеры в Kubernetes.
    Студент, который пойдёт работать с кластером, увидит там те же
    container_* ряды и ту же логику запросов;
  * готовый дашборд 11467 из практики 5 рассчитан именно на cAdvisor.

Честная оговорка про цену: cAdvisor на машине с сотней контейнеров
отдаёт десятки тысяч рядов и сам потребляет заметную долю процессора.
Если нужны только метаданные, docker_exporter дешевле. Если нужны
метрики потребления, альтернатив cAdvisor в курсе нет.

ЗАЧЕМ ЭТО В РАБОТЕ: большинство экспортёров в курсе устроены одинаково —
они читают чужое состояние и переводят его в формат exposition. Этот
шаг показывает, что выбирать экспортёр — значит выбирать, какое именно
состояние вам нужно, а не «какой популярнее». Дальше та же мысль
встретится в практике 13, когда понадобится свой экспортёр.

Уберём docker_exporter: в дальнейшей работе он не нужен.

  docker stop docker-exporter && docker rm docker-exporter

=========================================================================
ШАГ 10. ВЕСЬ МОНИТОРИНГ ЦЕЛИКОМ В COMPOSE
=========================================================================

До сих пор мы работали так: Prometheus стоит службой systemd на mon,
cAdvisor — контейнером на app1. Это смешанная схема, и она самая
распространённая в работе. Но есть случай, когда её применить нельзя:
машина, на которой запрещено ставить пакеты и заводить службы. Типовая
причина — не техническая, а организационная: на машине нет прав root,
или всё, что на ней запускается, должно быть контейнером, чтобы его
можно было удалить одной командой.

Тогда весь мониторинг собирается в docker compose и запускается одной
командой. В этом есть и учебная польза: собрав Prometheus, Grafana,
node_exporter и cAdvisor в один файл, видно, из чего мониторинг состоит
на самом деле. Мы уже знаем каждую часть по отдельности, и теперь они
складываются вместе.

Файл целиком лежит в files/07_containers/docker-compose.yml.
Он напечатан ниже до символа:

  # files/07_containers/docker-compose.yml
  #
  # Стек мониторинга целиком в контейнерах, для машины app1.
  #
  # Запуск:    docker compose up -d
  # Остановка: docker compose down
  #
  # ВАЖНО: Grafana публикуется на 3001, а не на 3000. Порт 3000
  # на стенде занят службой Grafana на машине mon.
  #
  # Тег latest не используется ни у одного образа: у каждого
  # указана конкретная версия. Причина разобрана в практике 7.

  services:

    # Хранилище метрик. Том prometheus_data переживает
    # пересоздание контейнера: без него история метрик
    # пропадёт при первом же docker compose down.
    prometheus:
      image: prom/prometheus:v3.15.0
      container_name: lab-prometheus
      restart: unless-stopped
      volumes:
        - ./prometheus.fragment.yml:/etc/prometheus/prometheus.yml:ro
        - prometheus_data:/prometheus
      command:
        - --config.file=/etc/prometheus/prometheus.yml
        - --storage.tsdb.path=/prometheus
        - --web.enable-lifecycle
      ports:
        - "9090:9090"

    # Grafana OSS 12.0.10. Том grafana_data хранит
    # пользователей, дашборды и источники данных: провижининг
    # здесь не настроен намеренно, чтобы было видно,
    # что именно теряется без тома.
    grafana:
      image: grafana/grafana-oss:12.0.10
      container_name: lab-grafana
      restart: unless-stopped
      depends_on:
        - prometheus
      volumes:
        - grafana_data:/var/lib/grafana
      ports:
        - "3001:3000"

    # node_exporter собирает метрики самой машины app1 —
    # те же, что отдаёт служба node_exporter из практики 2.
    # Порт 9100 на app1 уже занят этой службой: перед
    # запуском стека она останавливается.
    node_exporter:
      image: prom/node-exporter:v1.12.1
      container_name: lab-node-exporter
      restart: unless-stopped
      command:
        - --path.procfs=/host/proc
        - --path.sysfs=/host/sys
        - --path.rootfs=/rootfs
      volumes:
        - /proc:/host/proc:ro
        - /sys:/host/sys:ro
        - /:/rootfs:ro
      ports:
        - "9100:9100"

    # cAdvisor читает статистику контейнеров из ядра хоста.
    # Ему нужны /sys и /var/lib/docker только для чтения,
    # а через /var/run/docker.sock он получает список
    # контейнеров. Режим ro у сокета запрещает менять сам
    # файл, но не запрещает разговаривать через него:
    # сокет двусторонний. Подробный разбор флагов —
    # в run_cadvisor.txt того же каталога.
    cadvisor:
      image: gcr.io/cadvisor/cadvisor:v0.55.1
      container_name: lab-cadvisor
      restart: unless-stopped
      privileged: true
      volumes:
        - /:/rootfs:ro
        - /var/run:/var/run:ro
        - /sys:/sys:ro
        - /var/lib/docker/:/var/lib/docker:ro
        - /dev/disk/:/dev/disk:ro
        - /var/run/docker.sock:/var/run/docker.sock:ro
      devices:
        - /dev/kmsg
      ports:
        - "8080:8080"

  volumes:
    prometheus_data:
    grafana_data:

Разберём файл по блокам. Читать его нужно не сверху вниз, а по смыслу:
сначала общая часть, потом каждый сервис.

  services
    Корневой ключ: под ним перечислены контейнеры стека. Имя сервиса
    (prometheus, grafana, node_exporter, cadvisor) — это внутренняя
    учётная единица compose. По этому имени контейнеры видят друг
    друга в сети compose: grafana при настройке источника данных
    обращается не к 10.0.2.13, а к prometheus.

  image
    Образ и версия. Все четыре закреплены: prom/prometheus:v3.15.0,
    grafana/grafana-oss:12.0.10, prom/node-exporter:v1.12.1,
    gcr.io/cadvisor/cadvisor:v0.55.1. Ни одного latest.

  container_name
    Имя контейнера в docker ps. Явное имя нужно, чтобы отличать
    контейнеры этого стека от контейнеров других стеков на машине.
    Без него compose добавит к имени префикс из имени каталога.

  restart: unless-stopped
    Политика перезапуска. Контейнер поднимется после перезагрузки
    машины, но не поднимется, если его остановили руками.

  volumes у Prometheus
    Два тома разного вида. Первый — привязка к файлу на машине
    (bind mount): ./prometheus.fragment.yml попадает в контейнер
    как /etc/prometheus/prometheus.yml, и режим ro запрещает
    контейнеру его менять. Второй — именованный том (named volume)
    prometheus_data, примонтированный в /prometheus: там живёт база
    данных. Именованный том переживает не только перезапуск
    контейнера, но и docker compose down; без него вся история
    метрик исчезнет при первой же остановке стека.

  command у Prometheus
    Аргументы запуска Prometheus. Два из них уже знакомы по практике 1:
    --config.file и --storage.tsdb.path. Срока хранения среди них нет,
    и это не упущение: в 3.15.0 флаг --storage.tsdb.retention.time
    помечен устаревшим, и значение 15d задано в самом
    prometheus.fragment.yml, в секции storage. Флаг
    --web.enable-lifecycle разрешает перезагрузку конфигурации
    запросом POST /-/reload, тем же способом, что и для службы
    на mon. Без него флаг не действует, и конфигурацию пришлось бы
    применять перезапуском контейнера.

  ports
    Публикация портов. Запись «9090:9090» читается так: внешний порт
    девять тысяч девяносто на машине, внутренний порт девять тысяч
    девяносто в контейнере. Кавычки не украшение: без них YAML
    разберёт значение как половинку часа, а не как строку. Это та же
    ловушка, что с интервалами без единиц в практике 2, только
    с другим исходом — compose её отвергнет с сообщением
    «Invalid port specification».

  depends_on у Grafana
    Порядок запуска: Grafana стартует после Prometheus. Честное
    предупреждение: depends_on отвечает за порядок запуска, а не
    за готовность. Prometheus может быть уже запущен и ещё не готов
    отвечать; Grafana в этом случае покажет ошибку при
    проверке источника данных, и проверку нужно повторить. Ждать
    готовности compose не умеет.

  node_exporter
    Метрики самой машины. Здесь важны три аргумента и три тома:
    --path.procfs, --path.sysfs и --path.rootfs указывают, где
    контейнеру искать /proc, /sys и корень. Внутри контейнера
    свои /proc и /sys, и они расскажут о контейнере, а не о машине;
    поэтому каталоги машины монтируются внутрь под другими именами
    (/host/proc, /host/sys, /rootfs) и указываются в аргументах.
    Это тот случай, когда без томов экспортёр формально работает,
    но показывает не то, что нужно.

  privileged у cAdvisor
    Тот же флаг, что в шаге 4, и то же следствие: контейнер
    доверенный. В compose это видно прямо в тексте файла, и это
    хорошо: опасное решение не спрятано.

  devices у cAdvisor
    Проброс устройства /dev/kmsg из машины в контейнер. Отдельный
    ключ, потому что устройства монтируются не так, как каталоги.

  volumes в конце файла
    Объявление именованных томов prometheus_data и grafana_data.
    Без этого блока compose не знает, что создавать, и откажется
    запускать стек. Пустое значение после двоеточия означает
    «том по умолчанию»: драйвер local, путь выбирает Docker.

ПОЧЕМУ ИМЕННО ТАК, про два вида томов. Привязка к файлу удобна для
конфигурации: правишь файл на машине и перезапускаешь контейнер.
Именованный том удобен для данных: Docker создаёт его сам и следит
за правами, а содержимое не зависит от того, где лежит файл compose.
Смешивать наоборот — конфигурацию в именованный том, а базу через
привязку к каталогу — можно, но тогда конфигурацию придётся копировать
внутрь тома командой docker cp, а база окажется в каталоге репозитория.

ЗАЧЕМ ЭТО В РАБОТЕ: файл compose — это описание того же мониторинга,
что мы собирали руками девять практик. Разница в том, что описание
хранится в системе контроля версий, а не в памяти инженера. Практика 15
разбирает эту мысль дальше: конфигурация мониторинга должна быть
воспроизводимой, а не «так исторически сложилось».

ШАГ 11. ЗАПУСК СТЕКА И КОНФЛИКТ ПОРТОВ

Перед запуском нужно освободить порты, которые займёт стек. На app1
уже работают: cAdvisor из шага 4 (порт 8080), служба node_exporter
из практики 2 (порт 9100) и наши контейнеры web-lab и cache-lab.

Готовим файл конфигурации рядом с файлом compose. В каталоге
files/07_containers/ уже лежит prometheus.fragment.yml; если compose
запускается не из этого каталога, скопируйте оба файла в одну папку:

  mkdir -p /home/engineer/lab-stack
  cd /home/engineer/lab-stack
  cp <путь к files/07_containers>/docker-compose.yml .
  cp <путь к files/07_containers>/prometheus.fragment.yml .

Останавливаем то, что мешает:

  docker stop cadvisor && docker rm cadvisor
  docker stop web-lab cache-lab && docker rm web-lab cache-lab
  sudo systemctl stop node_exporter

Службу node_exporter останавливаем, а не удаляем: в практике 10 она
понадобится снова, и тогда достаточно будет команды systemctl start.

Запускаем стек:

  cd /home/engineer/lab-stack
  docker compose up -d
  [+] Running 6/6
   ✔ Network lab-stack_default       Created
   ✔ Volume "lab-stack_prometheus_data"  Created
   ✔ Volume "lab-stack_grafana_data"     Created
   ✔ Container lab-node-exporter     Started
   ✔ Container lab-cadvisor          Started
   ✔ Container lab-prometheus        Started
   ✔ Container lab-grafana           Started

Проверяем, что всё поднялось:

  docker compose ps
  NAME                IMAGE                              STATUS         PORTS
  lab-cadvisor        gcr.io/cadvisor/cadvisor:v0.55.1   Up 20 seconds  0.0.0.0:8080->8080/tcp
  lab-grafana         grafana/grafana-oss:12.0.10        Up 15 seconds  0.0.0.0:3001->3000/tcp
  lab-node-exporter   prom/node-exporter:v1.12.1         Up 18 seconds  0.0.0.0:9100->9100/tcp
  lab-prometheus      prom/prometheus:v3.15.0            Up 17 seconds  0.0.0.0:9090->9090/tcp

Prometheus этого стека открывается на http://10.0.2.13:9090,
Grafana — на http://10.0.2.13:3001.

Теперь про порт Grafana. В файле написано "3001:3000", и это место,
где чаще всего возникает вопрос «почему не 3000». Причина в стенде:
порт 3000 уже занят службой Grafana на машине mon из практики 5.
Машины разные, и формально конфликта нет: 3000 на mon и 3000 на app1 —
разные порты на разных адресах. Но есть два практических следствия,
и оба неприятные:

  * привычка. Студент и преподаватель помнят «Grafana — это 3000».
    Открывая 3000 на app1, можно попасть на Grafana с mon, если
    браузер подставил адрес из истории, и потом долго искать,
    почему в ней нет дашбордов из этого стека;
  * перенос файла. Файл compose обычно живёт в репозитории и рано
    или поздно попадает на машину, где 3000 занят. Тогда запуск
    заканчивается ошибкой, и разбираться в ней придётся в спешке.

ВАЖНО: порт 3001 в этом файле — не «так удобнее», а осознанное
решение, о котором сказано в самом файле. Если вы будете использовать
этот файл на своей машине, где 3000 свободен, поменяйте строку
на "3000:3000", но помните: правка порта в одном месте требует правки
адреса в другом — в настройках источника данных Grafana и в ссылках.

Настроим источник данных Grafana в этом стеке. Заходим на
http://10.0.2.13:3001, входим как admin/admin, меняем пароль.
Дальше Connections → Data sources → Prometheus, и в поле URL пишем
не 10.0.2.13:9090, а адрес контейнера в сети compose:

  http://prometheus:9090

ПОЧЕМУ ИМЕННО ТАК: внутри сети compose у контейнеров есть имена,
и они разрешаются во внутренние адреса. Grafana и Prometheus видят
друг друга по именам сервисов. Адрес 10.0.2.13 тоже сработал бы,
но он лишний: он привязывает конфигурацию к конкретной машине.

Проверяем результат запросом в Prometheus этого стека:

  count(up)
  2

Две цели: сам Prometheus и node_exporter. cAdvisor здесь целью не стал:
в этом стеке у Prometheus другой файл конфигурации, и задания docker
в нём нет — в fragment из шага 5 оно есть, но этот файл показывает
устройство compose, а не повторяет всю конфигурацию стенда. Добавьте
задание docker самостоятельно, если хотите увидеть контейнеры
в этом стеке: файл примонтирован с машины, и правка на машине
подействует после перезапуска контейнера Prometheus.

ПРОВЕРКА: команда docker compose logs --tail 5 prometheus не содержит
строк с ошибками, и в выводе есть строка вида:

  msg="Server is ready to receive web requests."


=========================================================================
ШАГ 12. SYSTEMD ИЛИ КОНТЕЙНЕРЫ: СРАВНЕНИЕ
=========================================================================

Мы собрали один и тот же мониторинг двумя способами. Подведём итог
таблицей, а потом скажем, что выбирают в работе и почему в ядре курса
остаётся systemd.

  | Что сравниваем | Службы systemd | Контейнеры (compose) |
  |---|---|---|
  | Где живёт конфигурация | /etc/prometheus/ | файл compose и тома |
  | Обновление версии | распаковать новый архив или apt | поменять тег образа |
  | Что видно при отказе | journalctl -u prometheus | docker logs |
  | Доступ к хосту | полный, процесс от prometheus | ограничен томами и флагами |
  | Нагрузка на диск | только данные | образы и слои, 1-2 ГБ |
  | Воспроизводимость | набор файлов и команд | один файл и одна команда |
  | Сколько учить | ничего нового после практики 1 | Docker, тома, сеть, образы |
  | Стоит на машине | везде, где есть права root | где root нет или нельзя пакеты |

Разберём два пункта, которые чаще всего решают исход выбора.

ПУНКТ ПЕРВЫЙ: доступ к хосту. Prometheus в контейнере ограничен тем,
что ему смонтировали. Это плюс с точки зрения безопасности и минус
с точки зрения диагностики: чтобы прочитать журнал службы или заглянуть
в каталог, придётся заходить на машину отдельно. Служба systemd живёт
в той же файловой системе, что и всё остальное, и лишних барьеров нет.

ПУНКТ ВТОРОЙ: воспроизводимость. Файл compose выигрывает у набора
команд из практик 1 и 2 — его можно положить в репозиторий и развернуть
на новой машине одной командой. Но выигрыш не бесплатный: чтобы этот
файл читать и править, нужно понимать Docker, тома, сети и политики
перезапуска. Это отдельный слой знаний, и в курсе он разбирается ровно
настолько, чтобы читать такой файл.

ПОЧЕМУ В ЯДРЕ КУРСА SYSTEMD, и это осознанное решение методики:

  * так видно устройство. Служба systemd — это юнит-файл, каталог
    конфигурации и каталог данных. Когда студент видит каждый из них
    отдельно, ему понятно, что именно сломалось, если служба
    не стартует. В контейнере эти же три вещи спрятаны за флагами;
  * так разбираются отказы. Классический отказ мониторинга — права
    на каталог данных. В службе он виден сообщением «Permission denied»
    и лечится один раз и навсегда. В контейнере он же выглядит как
    «том смонтирован не туда», и это другая диагностика;
  * так меньше слоёв между студентом и предметом. Курс про мониторинг,
    а не про контейнеры: если бы Prometheus с самого начала стоял
    в контейнере, каждая ошибка могла бы оказаться ошибкой Docker.

ЧЕГО НЕ ДЕЛАТЬ: не превращайте это сравнение в спор «что лучше».
В большинстве рабочих сред встречаются оба способа одновременно,
и это нормально: базы и очереди живут в контейнерах, экспортёры
на узлах — службами, а мониторинг где-то посередине. Выбирать нужно
по двум вопросам: есть ли права ставить службы и нужен ли доступ
к железным метрикам машины. Если прав нет — контейнеры. Если нужны
метрики самой машины из контейнера — придётся монтировать /proc, /sys
и корень, как в node_exporter этого стека, и это уже компромисс.

ЗАЧЕМ ЭТО В РАБОТЕ: точно такой же выбор встаёт при развёртывании
Alertmanager в практике 9 и при обновлении компонентов в практике 15.
Ответ зависит от того, кто и как обслуживает машину, а не от того,
какой способ новее.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: permission denied while trying to connect to the Docker daemon
socket at unix:///var/run/docker.sock

Причина: учётная запись engineer не входит в группу docker либо входит,
но текущая сессия об этом ещё не знает. Группы применяются при входе
в систему, и уже открытая сессия остаётся с прежним набором.

Порядок проверки. Первым делом смотрим состав групп:

  id
  uid=1000(engineer) gid=1000(engineer) groups=1000(engineer),27(sudo)

Если группы docker в выводе нет, добавляем и входим заново:

  sudo usermod -aG docker engineer
  exit
  ssh engineer@10.0.2.13

Вторым делом проверяем права на файл сокета:

  ls -l /var/run/docker.sock
  srw-rw---- 1 root docker 0 ... /var/run/docker.sock

Если группа docker в выводе есть, а команда всё равно отказывает,
проверяем, тот ли это сокет: переменная DOCKER_HOST могла остаться
от прошлых экспериментов.

  echo $DOCKER_HOST

Пустая строка — норма. Любое значение — причина отказа.

ЧЕГО НЕ ДЕЛАТЬ: не лечите это через sudo docker. Команда заработает,
но проблема останется, а вы будете запускать каждый следующий шаг
от root и не заметите, когда что-то пойдёт не так именно из-за прав.


ПРОБЛЕМА: cAdvisor в состоянии Restarting, в docker ps бесконечный
перезапуск, в логах строка вида

  Failed to create a Container Manager: failed to find cgroup mountpoint

Причина: не примонтирован /sys или не хватает прав. cAdvisor читает
иерархию cgroup из /sys/fs/cgroup; без этого тома он не может
инициализироваться и падает, а политика перезапуска поднимает его
снова. Внешне это выглядит как «cAdvisor сломан», хотя дело в команде
запуска.

Порядок проверки. Первым делом смотрим состояние и логи:

  docker ps --filter name=cadvisor
  docker logs --tail 20 cadvisor

Вторым делом сверяем команду запуска с той, что в
files/07_containers/run_cadvisor.txt: в ней должны быть --privileged,
--volume /sys:/sys:ro и --volume /var/lib/docker/:/var/lib/docker:ro.
Третьим — проверяем, что каталог cgroup существует на машине и что
мы во второй версии cgroup:

  ls /sys/fs/cgroup/
  stat -fc %T /sys/fs/cgroup/
  cgroup2fs

Если тома на месте и cgroup второй версии, пересоздаём контейнер:

  docker stop cadvisor && docker rm cadvisor
  <команда docker run из run_cadvisor.txt>

ПОЧЕМУ ИМЕННО ТАК: cgroup v2 стал обычным в Ubuntu 26.04, и старые
инструкции из интернета, написанные для cgroup v1, иногда предлагают
монтировать /sys/fs/cgroup/tmpfs отдельно. Для cgroup v2 это не нужно
и может только помешать.


ПРОБЛЕМА: метрики container_* собираются, но у них нет метки name,
а есть только id

Симптом: запрос container_memory_working_set_bytes{job="docker"}
возвращает ряды, но в подписи вместо web-lab стоит длинный
идентификатор. Фильтр name!="" отбрасывает всё, и график пустой.

Причина: cAdvisor не получил доступ к API демона Docker. Без сокета
он видит cgroup и может их измерить, но не знает, какому контейнеру
соответствует каждая группа. Метки id при этом хватает, поэтому метрики
есть, а имён нет.

Порядок проверки. Первым делом — есть ли сокет внутри контейнера:

  docker exec cadvisor ls -l /var/run/docker.sock

Вторым — видит ли cAdvisor контейнеры вообще:

  curl -s http://localhost:8080/api/v1.3/containers | head -20

Третьим — нет ли ошибки в логах cAdvisor о подключении к Docker:

  docker logs cadvisor 2>&1 | grep -i docker | head

Если сокета внутри нет, команда запуска собрана без тома
/var/run/docker.sock. Это самая частая причина: том можно потерять
при копировании команды из чата или из старой инструкции.

ЗАЧЕМ ЭТО В РАБОТЕ: отсутствие метки name — не косметика. Дашборд,
построенный на группировке по name, при этом пустой, и человек
ищет ошибку в запросе, а не в команде запуска экспортёра. Смотреть
сначала на экспортёр, потом на запрос — правило, которое экономит
время.


ПРОБЛЕМА: при запуске стека compose отвечает

  Error response from daemon: driver failed programming external
  connectivity on endpoint lab-grafana: Bind for 0.0.0.0:3001 failed:
  port is already allocated

Причина: порт уже занят другим процессом на этой же машине. Классика —
второй запуск того же стека (первый контейнер ещё жив) или чужая
служба на этом порту. На стенде бывает и третий случай: студент
поменял в файле 3001 на 3000, а на машине уже работает Grafana
из пакета.

Порядок проверки. Первым делом — кто держит порт:

  sudo ss -ltnp | grep -E ':(3000|3001|8080|9090|9100)\b'

Вторым — не поднят ли уже этот стек:

  docker compose ps
  docker ps -a --filter name=lab-

Третьим — что говорит сам compose о состоянии проекта:

  docker compose down
  docker compose up -d

Если порт держит не наш контейнер, освобождать его нужно осознанно:
на mon это служба Grafana, которая нужна для практик 5 и 10, и гасить
её ради стека на app1 нельзя. Правильное решение в этом случае —
оставить в файле 3001.

ИСПРАВЛЕНО: стек мониторинга в контейнерах прежняя версия курса
не собирала: compose в ней не упоминается ни разу, cAdvisor и метрики
container_* не разбирались. Конфликт портов 3000 и 3001 — реальная
ошибка, которую делают при переносе compose-файла на машину, где уже
работает служба Grafana из пакета: compose отвечает port is already
allocated, и стек не поднимается. Здесь эта ошибка разобрана заранее,
чтобы на стенде она не выглядела поломкой стенда.

Проверяем работу по шагам. Каждый пункт — команда и ожидаемый
результат.

1. Docker установлен и работает:

     docker --version
     Docker version 28.5.1, build ...

     sudo systemctl is-active docker
     active

2. engineer работает с Docker без sudo:

     docker ps --format '{{.Names}}'
     (список контейнеров без ошибки прав)

3. cAdvisor отдаёт метрики контейнеров:

     curl -s http://10.0.2.13:8080/healthz
     ok

     curl -s http://10.0.2.13:8080/metrics | grep -c '^container_'
     1840        (порядок величины, не точное число)

4. Задание docker в Prometheus зелёное. На странице
   http://10.0.2.5:9090/targets цель 10.0.2.13:8080 в состоянии UP,
   в метках есть job=«docker» и env=«lab».

5. Метрики контейнеров видны по именам, а не только по id:

     count(count by (name) (container_last_seen{job="docker", name!=""}))
     3           (не меньше числа работающих контейнеров)

6. Четыре ключевые метрики отвечают. Проверяем на вкладке Graph
   по очереди:

     rate(container_cpu_usage_seconds_total{name="web-lab"}[5m])
     container_memory_working_set_bytes{name="web-lab"}
     rate(container_network_receive_bytes_total{name="web-lab"}[5m])
     container_fs_usage_bytes{name="web-lab"}

   Каждый запрос возвращает непустой результат.

7. Значения сходятся с docker stats. Запускаем docker stats
   и запрос загрузки процессора по контейнерам; значения отличаются
   не более чем на несколько процентов и запаздывают на интервал сбора.

     docker stats --no-stream
     sum by (name) (rate(container_cpu_usage_seconds_total{job="docker", name!=""}[5m]))

8. Метрики демона Docker включены:

     curl -s http://127.0.0.1:9323/metrics | grep -c '^engine_'
     (число больше нуля)

9. Стек в compose работает:

     docker compose ps
     (четыре контейнера в состоянии Up)

     curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.13:9090/-/healthy
     200

     curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.13:3001/login
     200

10. Вы можете объяснить своими словами:

     * почему метрика container_cpu_usage_seconds_total — счётчик
       и почему к ней нужен rate;
     * почему instance у метрик контейнера равен адресу cAdvisor,
       а не адресу контейнера;
     * чем монтирование docker.sock отличается от обычного тома
       только для чтения;
     * почему Grafana в compose опубликована на 3001;
     * что вы выбрали бы на своей машине — службы или контейнеры —
       и по каким двум признакам.


=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Мы научились измерять контейнеры и собрали мониторинг в контейнерах.
Следующая практика отвечает на вопрос, который к этому моменту уже
назрел: метрик много, смотреть на них глазами невозможно, а дежурный
не может сидеть в веб-интерфейсе круглосуточно. Значит, условия нужно
описать заранее — правилами.

Далее в курсе:

  * практика 8 — правила записи и оповещения: те же запросы
    к container_* и node_* метрикам превращаются в правила, которые
    вычисляются всегда, а не пока открыт браузер;
  * практика 9 — Alertmanager: правило из практики 8 доводится
    до человека, и там же выяснится, почему правило без получателя
    никого не разбудит;
  * практика 10 — итоговая работа трека «3 дня»: стек на app1
    и службы на остальных машинах проверяются одним чек-листом.

ПЕРЕД ПЕРЕХОДОМ уберите за собой. Стек в compose остановите, данные
пока сохраните — они понадобятся в практике 8 для проверки правил:

  cd /home/engineer/lab-stack
  docker compose stop

Службу node_exporter на app1 верните: без неё задание node потеряет
одну цель, а в практике 8 на нём построено оповещение InstanceDown:

  sudo systemctl start node_exporter
  systemctl is-active node_exporter

Контейнеры web-lab и cache-lab можно оставить остановленными;
если они больше не нужны, удалите их вместе с томами:

  docker rm -f web-lab cache-lab 2>/dev/null
  docker volume prune -f

Данные стека удалять не нужно: docker compose stop останавливает
контейнеры, но оставляет тома prometheus_data и grafana_data на месте.
Удалять их стоит только тогда, когда вы уверены, что история метрик
больше не нужна: команда docker compose down -v удаляет тома вместе
с контейнерами, и восстановить данные будет неоткуда.
