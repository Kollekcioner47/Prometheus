# Параметры хранения Prometheus на стенде курса.
#
# Таблица отвечает на три вопроса по каждому параметру: что он
# делает, какое значение стоит в курсе и что будет при изменении.

## Где задаётся хранение

| Параметр | Где | Что делает | Значение в курсе |
|---|---|---|---|
| storage.tsdb.retention.time | prometheus.yml | Сколько времени хранить блоки | 15d |
| storage.tsdb.retention.size | prometheus.yml | Предельный объём блоков на диске | Не задан |
| --storage.tsdb.path | юнит-файл | Каталог локальной базы: wal, блоки, chunks_head | /var/lib/prometheus |
| --web.enable-admin-api | юнит-файл | Удаление рядов через API | Выключен |

## Параметры, которые мы не трогаем

| Параметр | Что делает | Почему не трогаем |
|---|---|---|
| --storage.tsdb.retention.time | Устаревшая форма срока по времени | Помечен [DEPRECATED] в 3.15.0 |
| --storage.tsdb.retention.size | Устаревшая форма предела по объёму | Помечен [DEPRECATED] в 3.15.0 |
| --storage.tsdb.wal-compression | Сжатие журнала (WAL) | Включено по умолчанию с 2.20 |
| --storage.tsdb.min-block-duration | Минимальная длительность блока | Служебный флаг для особых случаев |
| --storage.tsdb.max-block-duration | Максимальная длительность блока | Служебный флаг для особых случаев |

Пояснения к строкам, которые чаще всего понимают неверно:

* retention.size считает только блоки. Журнал wal в этот объём
  не входит, поэтому диск может заполниться журналом при заданном
  пределе размера;
* min-block-duration и max-block-duration в документированном
  наборе флагов отсутствуют: это служебные параметры, и меняют их
  только тогда, когда рядом работает Thanos sidecar — ему нужны
  блоки по два часа без укрупнения;
* --web.enable-admin-api в курсе выключен намеренно. Этот флаг
  разрешает удалять ряды через API, и снаружи это опасная ручка.

## Что побеждает: время или размер

Оба предела действуют одновременно, и данные удаляются тогда,
когда сработал **любой** из них. retention.size не продлевает
хранение, а только сокращает его: если места мало, старые блоки
удаляются раньше срока. Обратное неверно — свободное место
не заставит базу хранить данные дольше retention.time.

Что происходит при исчерпании диска:

* Prometheus не может записать блок, в журнале появляется
  err="ran out of space";
* сбор продолжается, но данные не сохраняются;
* при дальнейшем отсутствии места процесс перезапускается
  по кругу, и systemctl status показывает
  Active: activating (auto-restart).

## Файлы и каталоги в /var/lib/prometheus

| Что | Что это |
|---|---|
| wal/ | Журнал: последние ~2 часа, отрезки по 128 МБ |
| chunks_head/ | Свежие образцы, ещё не уложенные в блок |
| 01H.../ | Готовый блок на 2 часа; имя — ULID |
| 01H....tmp/ | Блок, который пишется прямо сейчас |
| lock | Блокировка каталога: второй Prometheus не стартует |
| queries.active | Список выполняющихся запросов |

Правило, по которому всё устроено: данные — в /var/lib/prometheus,
владелец — учётная запись prometheus. Ошибка прав здесь выглядит
как Error opening storage: ... permission denied, и это первая
причина, которую проверяют, когда Prometheus не стартует.

## Retention: почему 15d, а не 10y

| Решение | Что за ним стоит |
|---|---|
| 15d в курсе | Стенд, диск 40 ГБ, интервал сбора 15s |
| 10y «на всякий случай» | Диск кончится за месяцы, а сбор откажет |
| 365d на сервере с SSD | Считается заранее по формуле ниже |
| Долгое хранение | Отдалённое хранилище, а не локальный retention |

Расчёт, который стоит делать до включения длинного хранения:
число рядов × 86400 / интервал_сбора_в_секундах — это число точек
в сутки. Умножьте на размер точки (в курсе считаем 1–2 байта
в сжатом блоке) и на число дней. Полученный объём сравните
со свободным местом честно, а не «примерно».
