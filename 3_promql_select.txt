Практика 3. PromQL: выборка и фильтрация.

ЭТА ПРАКТИКА — ПЕРВАЯ ИЗ ДВУХ ПРАКТИК ПРО ЯЗЫК ЗАПРОСОВ. Здесь мы учимся
выбирать ряды: находить нужную метрику, отбирать её по меткам, сдвигать
запрос во времени и отличать «значение равно нулю» от «ряда нет вообще».
Считать мы пока не будем: арифметика, агрегация и rate — это практика 4.
Опирается практика на ряды и метки, которые появились в практике 2.

=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Разберём, зачем нужен язык запросов и почему без него дашборд
бесполезен. Познакомимся с вкладкой Graph в веб-интерфейсе
Prometheus: поле запроса, кнопка Execute, переключатели Table
и Graph, диапазон времени и шаг. Разберём два вида векторов —
мгновенный и диапазонный — и увидим ошибку, которую даёт
диапазонный вектор там, где ожидается мгновенный. Научимся
отбирать ряды по меткам операторами =, !=, =~ и !~ и понимать,
почему регулярное выражение в PromQL привязано к строке целиком.
Разберём специальные метки __name__, job, instance, env и поиск
метрики по части имени. Сдвинем запрос во времени через offset
и @, посмотрим разницу между вкладками Table и Graph и научимся
честно отвечать на вопрос «а что, если данных нет» — функциями
absent() и absent_over_time() и метрикой up. Закончим запросом
count(up) — первым шагом к агрегации.

=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

ПЯТЬ МАШИН СТЕНДА, ИЗ НИХ ЧЕТЫРЕ С ЭКСПОРТЁРАМИ. Практика 2
выполнена: node_exporter 1.12.1 работает на mon, web1, db1 и app1,
и на странице Status -> Targets пять целей в состоянии UP.

  mon    10.0.2.5    Prometheus 3.15.0, node_exporter 1.12.1
  web1   10.0.2.11   node_exporter 1.12.1
  db1    10.0.2.12   node_exporter 1.12.1
  app1   10.0.2.13   node_exporter 1.12.1

ЧТО НУЖНО ПРОВЕРИТЬ ДО НАЧАЛА. Prometheus собирает данные
с интервалом 15s и хранит их 15d. Запросы, которые мы будем
делать в шагах 8 и 9, смотрят на данные за прошедшее время,
поэтому практику лучше начинать не в первую минуту после
установки экспортёров: к моменту занятия в базе должно лежать
хотя бы несколько часов рядов.

ФАЙЛЫ ИЗ КУРСА, каталог files/03_promql_select:

  * queries.promql — все запросы практики отдельными строками,
    с комментариями и примерами absent-запросов.

Ниже напечатан полный текст этого файла: те же запросы в том же
порядке, что и в шагах. Его удобно держать открытым рядом
с браузером.

  # files/03_promql_select/queries.promql
  # Запросы практики 3 «PromQL: выборка и фильтрация».
  # Считать здесь нечего: rate, агрегация и histogram_quantile — это
  # практика 4. Исключение — count(up) в конце файла: это мостик.
  # Каждый запрос записан одной строкой, чтобы его было удобно
  # скопировать в поле Expression на странице http://10.0.2.5:9090/graph.


  # --- ШАГ 1. ЯЗЫК ЗАПРОСОВ И ВКЛАДКА GRAPH --------------------------
  # Простейший запрос: пять рядов на стенде, по одному на каждую цель.

  up


  # --- ШАГ 2. МГНОВЕННЫЙ И ДИАПАЗОННЫЙ ВЕКТОР -----------------------
  # Мгновенный вектор: одно значение на ряд, это и есть ответ.

  node_load1

  # Мгновенный вектор, суженный до одной машины.

  node_load1{instance="10.0.2.11:9100"}

  # Диапазонный вектор. Сам по себе в поле Expression даёт ошибку:
  # invalid expression type "range vector" for range query,
  # must be Scalar or instant Vector. Он годится только как аргумент
  # функции — ниже два примера таких функций из практики 4.

  node_load1[5m]
  node_load1{instance="10.0.2.11:9100"}[5m]

  # Диапазонный вектор внутри функции выполняется и отвечает
  # на вопрос «сколько точек было в окне».

  count_over_time(node_load1[5m])
  avg_over_time(node_load1[5m])


  # --- ШАГ 3. СЕЛЕКТОРЫ И ОПЕРАТОРЫ СОПОСТАВЛЕНИЯ --------------------
  # Селектор — имя метрики плюс условия на метки. Пустой селектор {}
  # запрещён: vector selector must contain at least one non-empty matcher.

  node_filesystem_avail_bytes{mountpoint="/"}
  node_cpu_seconds_total{mode!="idle"}
  node_network_receive_bytes_total{device=~"ens.*"}
  node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}

  # Регулярное выражение привязано к значению метки целиком:
  # device=~"ens" не найдёт ens3, а device=~"ens.*" найдёт.
  # Синтаксис RE2: без обратных ссылок и опережающих проверок.

  node_network_receive_bytes_total{device="ens3"}
  node_network_receive_bytes_total{device=~"ens.*"}

  # Ровно одна машина и ровно один режим процессора: без метки cpu
  # запрос вернёт по строке на каждое ядро.

  node_cpu_seconds_total{instance="10.0.2.12:9100",mode="idle"}

  # Отбор по нескольким меткам сразу.

  node_load1{job="node",instance="10.0.2.11:9100"}


  # --- ШАГ 4. СПЕЦИАЛЬНЫЕ МЕТКИ: __NAME__, JOB, INSTANCE, ENV --------
  # Эти две записи означают одно и то же: имя метрики и метка __name__.

  node_load1
  node_load1{__name__="node_load1"}

  # Поиск метрики по части имени. Выражение ограничено префиксом:
  # node_load.+, а не .+ — иначе запрос выбирает всю базу.

  {__name__=~"node_load.+"}

  # Обзор с ограничением по заданию: так делают, когда нужен список
  # метрик, а не одна конкретная. Без ограничения job запрос вреден.

  {__name__=~"node_.+",job="node"}
  {__name__=~".+",job="node"}

  # Отбор по внешней метке env, которую добавил Prometheus
  # из external_labels, и по метке job.

  up{env="lab"}
  up{job="node"}


  # --- ШАГ 5. ВКЛАДКИ TABLE И GRAPH ---------------------------------
  # Одна метрика на одной машине даёт три ряда: три точки монтирования.
  # На вкладке Table это видно сразу, на графике — только по легенде.

  node_filesystem_avail_bytes

  # Подсчёт строк по значению метки: сколько у метрики разных значений.

  count by (mountpoint) (node_filesystem_avail_bytes)


  # --- ШАГ 6. СДВИГ ВО ВРЕМЕНИ: OFFSET И @ --------------------------
  # offset сдвигает запрос назад во времени.

  node_load1 offset 1h
  node_load1 offset 5m
  node_load1{instance="10.0.2.11:9100"} offset 30m

  # Сравнение «вчера и сегодня»: два запроса на одном диапазоне.

  node_filesystem_avail_bytes{mountpoint="/"}
  node_filesystem_avail_bytes{mountpoint="/"} offset 24h

  # @ фиксирует момент времени. Время — секунды эпохи Unix,
  # а не миллисекунды: 1700000000 — это 14 ноября 2023 года.

  node_load1 @ 1700000000

  # start() и end() — края выбранного на графике диапазона.

  node_load1 @ start()
  node_load1 @ end()


  # --- ШАГ 7. НОЛЬ ИЛИ НЕТ РЯДА: ABSENT() И ABSENT_OVER_TIME() -------
  # absent() возвращает ряд со значением 1, если переданного ряда
  # нет, и пустоту, если ряд есть. Меток у результата нет.

  absent(node_load1{instance="10.0.2.11:9100"})
  absent(node_load1{instance="10.0.2.99:9100"})

  # absent_over_time() отвечает не «есть ли ряд сейчас», а «были ли
  # у него точки за окно»: пропуск сбора он замечает, absent() — нет.

  absent_over_time(node_load1{instance="10.0.2.11:9100"}[1h])

  # Разница между «0» и «нет ряда»: первый запрос вернёт значение
  # (0 при остановленном экспортёре), второй — пустоту.

  up{instance="10.0.2.11:9100"}
  up{instance="10.0.2.99:9100"}


  # --- ШАГ 8. UP КАК ИНДИКАТОР СВЯЗИ --------------------------------
  # up == 0 означает «не смогли собрать метрики», а не «машина упала».

  up{job="node"} == 0

  # absent(up) отвечает на другой вопрос: задания нет вовсе.

  absent(up{job="node"})


  # --- ШАГ 9. COUNT(UP) КАК МОСТИК К ПРАКТИКЕ 4 ---------------------
  # count — уже агрегация, и подробно она разбирается в практике 4.
  # Здесь она нужна только чтобы перешагнуть к ней.

  count(up)
  count(up{env="lab"})
  count by (job) (up)
  count by (job, env) (up)
  count without (instance) (up)

СКОЛЬКО ЭТО ЗАЙМЁТ: 3 академических часа. Практика почти целиком
проходит в браузере: мы пишем запросы и читаем, что получилось,
а не настраиваем службы.

ЧЕГО В ЭТОЙ ПРАКТИКЕ НЕ БУДЕТ. Мы не трогаем функции для
счётчиков (rate, increase), не считаем квантили и не агрегируем
ряды. Агрегация появится в практике 4 «PromQL: вычисления»,
и там же разберётся, почему avg по счётчику — плохая идея.
Единственное исключение — count(up) в последнем шаге: это
мостик, а не полноценная агрегация.

#########################################################################
ЧАСТЬ 1. ВЫБОРКА: СЕЛЕКТОРЫ, МЕТКИ И ПОИСК
#########################################################################

=========================================================================
ШАГ 1. ЯЗЫК ЗАПРОСОВ И ВКЛАДКА GRAPH
=========================================================================

Откройте http://10.0.2.5:9090/graph. Это основная рабочая
страница курса: половина практик проходит здесь.

ЧТО НА СТРАНИЦЕ:

  * поле запроса (Expression) — сюда пишется выражение PromQL;
  * кнопка Execute — выполняет запрос;
  * переключатели Table и Graph — два способа показать результат;
  * поле диапазона времени рядом с Graph — за какой период
    рисовать график;
  * поле Resolution — шаг, с которым точки берутся из базы.

ЧТО ПРОИСХОДИТ ПРИ НАЖАТИИ EXECUTE. Prometheus берёт текст
из поля, разбирает его, выполняет и показывает результат
в выбранном виде. Поле запроса подсказывает имена метрик
и функций по первым буквам.

Введите простейший запрос:

  up

Нажмите Execute. В режиме Table вы увидите строки:

  Element                                                              Value
  up{env="lab", instance="10.0.2.5:9090", job="prometheus"}            1
  up{env="lab", instance="10.0.2.5:9100", job="node"}                  1
  up{env="lab", instance="10.0.2.11:9100", job="node"}                 1
  up{env="lab", instance="10.0.2.12:9100", job="node"}                 1
  up{env="lab", instance="10.0.2.13:9100", job="node"}                 1

Пять строк — пять целей. Колонка Element показывает имя метрики
и полный набор меток ряда, колонка Value — значение.

ПОЧЕМУ ИМЕННО ТАК: у Prometheus нет отдельной «страницы метрик» со списком и
  поиском, как в Zabbix. Вместо неё — язык запросов: список рядов получают
  запросом, а не обходом дерева. Это непривычно в первый день и заметно
  удобнее на второй: любой отбор, который вы однажды написали, можно
  переиспользовать в дашборде, в правиле и в API.

ЗАЧЕМ ЭТО В РАБОТЕ: дежурный отвечает на вопросы именно здесь. «Сколько
  машин отдаёт метрики», «какая цель пропала», «что было вчера в семь
  вечера» — это три запроса, а не три похода по меню.

ПРОВЕРКА: убедитесь, что страница отвечает и запрос выполняется. Тот же
  запрос можно выполнить без браузера, через API:

    curl -s 'http://localhost:9090/api/v1/query?query=up' | head -c 400

  Ответ в формате JSON с полем "resultType":"vector". Если
  Prometheus недоступен, curl вернёт пустоту, а команда —
  код ошибки; это первое, что стоит проверить, когда
  «браузер не показывает данные».

=========================================================================
ШАГ 2. МГНОВЕННЫЙ И ДИАПАЗОННЫЙ ВЕКТОР
=========================================================================

В PromQL результат почти каждого выражения — это вектор.
Векторов два вида, и различать их нужно с самого начала,
потому что от этого зависит, какие функции применимы.

МГНОВЕННЫЙ ВЕКТОР (instant vector) — набор рядов, у каждого
ровно одно значение на выбранный момент времени:

  node_load1
  node_load1{instance="10.0.2.11:9100"}

Запрос node_load1 вернёт четыре ряда — по одному на машину —
и у каждого одно значение: загрузка прямо сейчас.

ДИАПАЗОННЫЙ ВЕКТОР (range vector) — набор рядов, у каждого
не одно значение, а несколько, за указанный промежуток времени:

  node_load1[5m]
  node_load1{instance="10.0.2.11:9100"}[5m]

Запрос node_load1[5m] вернёт по пять минут значений на каждый
ряд — примерно двадцать точек при интервале сбора 15 секунд.

ПОЧЕМУ node_load1 РАБОТАЕТ, А node_load1[5m] НЕ РАБОТАЕТ.
Введите в поле запроса ровно это:

  node_load1[5m]

Нажмите Execute и получите ошибку:

  Error executing query: invalid expression type "range vector" for range query, must be Scalar or instant Vector

Смысл сообщения: страница Graph сама строит график, то есть
выполняет запрос как диапазонный — ей нужны значения на много
моментов времени. Она ожидает мгновенный вектор и уже из него
делает точки. Если вы дали ей диапазонный вектор, она не может
сделать из него график: непонятно, какое из двадцати значений
рисовать.

Диапазонный вектор — это не самостоятельный ответ, а аргумент
для функций, которые умеют работать с набором точек: rate,
increase, avg_over_time, max_over_time, count_over_time. Все они
появятся в практике 4. Общее правило: квадратные скобки
с длительностью стоят только внутри функции.

ПОЧЕМУ ИМЕННО ТАК: диапазонный вектор не может быть ответом на запрос,
  потому что у него нет одного значения на ряд. Если бы Prometheus
  согласился его показать, каждый ряд пришлось бы выводить как двадцать
  значений, и ни один график из этого не собрался бы.

ЧЕГО НЕ ДЕЛАТЬ: не пытайтесь обойти ошибку, дописав к запросу что-нибудь
  наугад (node_load1[5m] + 0, node_load1[5m] @ end()). Правильный вопрос
  звучит иначе: «что я хочу сделать с этими пятью минутами?» Если
  усреднить — нужна avg_over_time, если узнать скорость — rate. Ответ на
  этот вопрос и есть выбор функции.

ВАЖНО: длительность в квадратных скобках пишется с единицей: [5m], [1h],
  [90s]. Запись [5] Prometheus не примет. Минимальный осмысленный диапазон
  — два интервала сбора: при 15s это [30s], и даже в нём будет всего две
  точки.

ПРОВЕРКА: посмотрите, что диапазонный вектор всё-таки существует, но только
  внутри функции. Запрос ниже выполнится и даст по четыре ряда, но это уже
  вычисление, а не выборка:

    count_over_time(node_load1[5m])

=========================================================================
ШАГ 3. СЕЛЕКТОРЫ И ОПЕРАТОРЫ СОПОСТАВЛЕНИЯ
=========================================================================

Селектор (selector) — это имя метрики плюс условия на метки.
Именно селектор решает, какие ряды попадут в результат.

ПРОСТОЙ СЕЛЕКТОР:

  node_load1

Он выбирает все ряды с этим именем: на стенде их четыре.
В практике 2 мы уже видели, что это значит «по одной строке
на каждую машину».

СЕЛЕКТОР С МЕТКОЙ:

  node_load1{instance="10.0.2.11:9100"}

Один ряд — загрузка web1. Обратите внимание на кавычки: значение
метки всегда в двойных кавычках, это не украшение, а требование
синтаксиса.

ПУСТОЙ СЕЛЕКТОР ЗАПРЕЩЁН:

  {}

Такой запрос вернёт ошибку разбора:

  Error executing query: parse error: vector selector must contain at least one non-empty matcher

Запрет осознанный. Запрос {} означает «все ряды вообще»: на стенде
это несколько тысяч рядов, на боевой системе — миллионы. Такой
запрос кладёт и браузер, и сам Prometheus. Если очень нужно
посмотреть «всё», это делают осознанно и через __name__, о чём
ниже.

ЧЕТЫРЕ ОПЕРАТОРА СОПОСТАВЛЕНИЯ:

  =    равно: mode="idle"
  !=   не равно: mode!="idle"
  =~   совпадает с регулярным выражением: mountpoint=~"/var.*"
  !~   не совпадает с регулярным выражением: device!~"/dev/loop.*"

Примеры на реальных метриках стенда:

  node_filesystem_avail_bytes{mountpoint="/"}
  node_cpu_seconds_total{mode!="idle"}
  node_network_receive_bytes_total{device=~"ens.*"}
  node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}

ПОЧЕМУ ИМЕННО ТАК: =~ вместо перечисления. Сравните два запроса:

    node_network_receive_bytes_total{device="ens3"}

    node_network_receive_bytes_total{device=~"ens.*"}

  Первый привязан к конкретному имени интерфейса. Второй
  переживает переименование ens3 в ens4 — а это происходит
  на стенде при клонировании машины, и на боевой системе
  при добавлении сетевого интерфейса. Запросы в дашбордах
  пишут так, чтобы они не ломались от смены имени устройства.

РЕГУЛЯРНЫЕ ВЫРАЖЕНИЯ ПРИВЯЗАНЫ (anchored). Это значит, что
выражение проверяется на совпадение со значением метки ЦЕЛИКОМ,
а не с любой её частью:

  device=~"ens"      не найдёт ens3: значение целиком не равно ens

  device=~"ens.*"    найдёт ens3: точка означает любой символ,
                     звёздочка — любое число повторений

  device=~".*ens.*"  тоже найдёт ens3, но это лишнее: привязка
                     уже выполнена за нас

  device!~"ens3"     исключит только точное значение ens3

Синтаксис регулярных выражений — RE2: он проще и предсказуемее
PCRE, в нём нет обратных ссылок и опережающих проверок. Полное
совпадение делается так же, как в примере: через .* по краям.

ЧЕГО НЕ ДЕЛАТЬ: не пишите {__name__=~".+"} на боевом сервере. Это
  замаскированный пустой селектор: выражение совпадает с любым именем
  метрики, и запрос выбирает всю базу. На стенде он выполнится за секунды,
  на системе с миллионами рядов — упрётся в таймаут и займёт память
  Prometheus. Если обзор нужен, его ограничивают заданием или префиксом
  имени метрики.

ПРОВЕРКА: подберите селектор, который вернёт ровно одну машину и ровно один
  режим процессора:

    node_cpu_seconds_total{instance="10.0.2.12:9100",mode="idle"}

  Если строк две, значит, вы забыли метку cpu: на каждой машине
  ядер больше одного, и ряд есть на каждое ядро.

=========================================================================
ШАГ 4. СПЕЦИАЛЬНЫЕ МЕТКИ: __NAME__, JOB, INSTANCE, ENV
=========================================================================

Кроме меток, которые отдал экспортёр, в ряде есть метки,
которыми управляет сам Prometheus. Их нужно знать, потому что
именно по ним чаще всего и отбирают.

__name__ — имя метрики. В обычной записи оно вынесено вперёд
и выглядит как часть выражения:

  node_load1

  node_load1{__name__="node_load1"}

Эти два запроса делают одно и то же. Второй нужен, когда имя
метрики задаётся регулярным выражением — тогда без __name__
не обойтись:

  {__name__=~"node_load.+"}

Этот запрос вернёт ряды node_load1, node_load5, node_load15
со всех машин. Именно так ищут метрику, когда помнят начало
имени, но не помнят точное.

ЧЕГО НЕ ДЕЛАТЬ: не превращайте поиск по имени в {__name__=~".+"}. Регулярное
  выражение node_load.+ ограничено по смыслу, а .+ означает всю базу. Если
  нужен именно обзор, добавьте ограничение по заданию:

    {__name__=~".+",job="node"}

job — имя задания из конфигурации. На стенде это prometheus
для самого Prometheus и node для четырёх машин с экспортёром.
Метка job отвечает на вопрос «каким способом собраны эти
метрики», и запрос up{job="node"} читается как «все цели,
которые опрашивает задание node».

instance — адрес цели. В курсе это адрес с портом экспортёра:
10.0.2.5:9100, 10.0.2.11:9100 и так далее. Для самого
Prometheus instance="localhost:9090".

env — метка внешняя. Экспортёр о ней не знает: её добавил
Prometheus из external_labels (env="lab") и из labels задания
node. Именно поэтому запрос up{env="lab"} на стенде вернёт
те же пять рядов, что и up: все цели стенда помечены одной
средой.

ПОЧЕМУ ИМЕННО ТАК: __name__, job, instance и env — обычные метки, а не
  особые поля. Из этого следует практическое: их можно указывать в
  селекторе наравне с cpu и mode, их можно переименовывать перемаркировкой
  (практика 11) и по ним можно группировать при агрегации (практика 4).

ЗАЧЕМ ЭТО В РАБОТЕ: когда в Grafana появится переменная дашборда со списком
  машин, она будет строиться запросом label_values(up, instance) — то есть
  перечислением значений метки instance. Понимание того, откуда эти метки
  берутся, убирает половину вопросов «почему в списке не та машина».

ПРОВЕРКА: посмотрите все значения метки job, которые есть в базе:

    count by (job) (up)

  Две строки: {job="node"} 4 и {job="prometheus"} 1. Если строк
  больше, значит, кроме практики 2, вы уже добавляли задания
  из следующих практик — это нормально, но помните об этом,
  когда читаете примеры вывода в курсе.

=========================================================================
ШАГ 5. ВКЛАДКИ TABLE И GRAPH
=========================================================================

Вкладка Table показывает результат как таблицу, и в ней
видно то, что на графике не видно вовсе: полный набор меток
каждого ряда.

Введите запрос:

  node_filesystem_avail_bytes

В Table вы увидите примерно такие строки (значения зависят
от стенда):

  Element                                                                       Value
  node_filesystem_avail_bytes{device="/dev/sda2",fstype="ext4",instance="10.0.2.5:9100",job="node",mountpoint="/"}   2.61823488e+10
  node_filesystem_avail_bytes{device="/dev/sdb1",fstype="ext4",instance="10.0.2.5:9100",job="node",mountpoint="/srv"}  8.39213056e+09
  node_filesystem_avail_bytes{device="tmpfs",fstype="tmpfs",instance="10.0.2.5:9100",job="node",mountpoint="/run"}   1.610612736e+09

ЧТО ЭТО ГОВОРИТ: одна метрика на одной машине дала три ряда,
потому что у неё три разных значения метки mountpoint. Диск,
tmpfs и точка монтирования /srv — разные ряды одного имени.
На графике в режиме Graph они слились бы в три линии, и без
меток было бы непонятно, какая из них какая.

Колонку Value можно сортировать — щёлкните по её заголовку.
Так можно ответить на вопрос «где хуже всего»,
не прибегая к функциям сортировки из практики 4:

  node_filesystem_avail_bytes{mountpoint="/"}

Сортировка работает по отображаемому значению, а не по
скрытому: результат тот же, что вы видите на экране.

ПОЧЕМУ ИМЕННО ТАК: вкладка Table — инструмент разбора, а не просмотра. На
  ней видно, что запрос вернул именно то, что нужно, и видно метки, по
  которым потом можно сгруппировать. Опытные инженеры начинают с Table и
  только потом переключаются на Graph.

ЧЕГО НЕ ДЕЛАТЬ: не выполняйте запросы без селектора на вкладке Table «чтобы
  посмотреть, что есть». Каждая строка таблицы — это ряд, переданный
  браузеру, и запрос вида node_.* с миллионом рядов отрисует страницу,
  которая не будет отвечать. Если нужен обзор, ограничивайте выборку: по
  заданию, по адресу, по конкретной метке.

ПРОВЕРКА: найдите метку, по которой у вас больше всего значений. Достаточно
  посмотреть на длину колонки Element:

    count by (mountpoint) (node_filesystem_avail_bytes)

  Агрегация здесь только для подсчёта строк; подробно она
  разбирается в практике 4.

ВКЛАДКА GRAPH показывает те же данные как временной ряд.
На ней есть диапазон времени и поле Resolution. Диапазон
задаёт, за какой период рисовать, Resolution — с каким шагом
брать точки. Если выбрать диапазон в тридцать дней, Prometheus
проредит данные и вернёт меньше точек, чем есть в базе: рисовать
два миллиона точек в браузере бессмысленно.

Расхождение между вкладками — частое место недоразумений:
запрос на вкладке Table считается на момент времени, а на
вкладке Graph — на весь диапазон. Пустая таблица при непустом
графике почти всегда означает, что выбран момент, когда ряда
ещё не было (или уже не было).

ЧАСТЬ 2. ВРЕМЯ, ПУСТОТА И ГРАНИЦА ВЫБОРКИ
#########################################################################

=========================================================================
ШАГ 6. СДВИГ ВО ВРЕМЕНИ: OFFSET И @
=========================================================================

Два временных модификатора позволяют задать, на какой момент
времени смотреть. Синтаксис у них разный, и оба встречаются
в работе постоянно.

OFFSET сдвигает запрос назад во времени на указанную
длительность. Запрос node_load1 offset 1h отвечает на вопрос
«какая была загрузка час назад», node_load1 offset 5m —
«пять минут назад».

  node_load1 offset 1h
  node_load1 offset 5m
  node_filesystem_avail_bytes{mountpoint="/"} offset 24h

Типичная задача — сравнить «вчера и сегодня»:

  node_filesystem_avail_bytes{mountpoint="/"}

  node_filesystem_avail_bytes{mountpoint="/"} offset 24h

Оба запроса можно выполнить по очереди на одном и том же
диапазоне времени: первый покажет, сколько места есть сейчас,
второй — сколько было сутки назад. Разница между ними и есть
ответ на вопрос «место кончается быстро или это разовая
запись». Считать разницу мы научимся в практике 4; пока
достаточно уметь посмотреть оба графика.

@ фиксирует момент времени, на который считается запрос.
Модификатор принимает секунды эпохи Unix:

  node_load1 @ 1700000000

Или одну из двух функций, привязанных к окну графика:

  node_load1 @ start()
  node_load1 @ end()

start() — начало выбранного диапазона, end() — его конец.
Запрос node_load1 @ end() на графике означает «значение
на правом краю окна»: линия станет горизонтальной, потому
что все точки берутся на один момент.

ВАЖНО: время в @ — это секунды эпохи Unix, а не миллисекунды. Если
  подставить миллисекунды (1700000000000), Prometheus попытается
  посмотреть в далёкое будущее и вернёт пустой результат — при этом
  синтаксически запрос верен, и ошибки не будет. Проверьте себя:
  1700000000 — это четырнадцатое ноября 2023 года.

ПОЧЕМУ ИМЕННО ТАК: offset не меняет интервал сбора и не ходит в архив. Он
  сдвигает только окно, из которого берутся данные. Поэтому offset 24h при
  сроке хранения 15d работает, а offset 30d вернёт пустоту: данных за
  тридцать дней в базе нет, и это честный ответ, а не ошибка.

ЗАЧЕМ ЭТО В РАБОТЕ: сравнение с прошлым — самый частый вопрос дежурного:
  «это нормально или только что стало так?» Без offset на него отвечают по
  памяти, а память за сутки врёт.

ПРОВЕРКА: убедитесь, что offset действительно работает, а не
  повторяет текущее значение. Сравните два запроса на вкладке Table:

    node_load1{instance="10.0.2.11:9100"}
    node_load1{instance="10.0.2.11:9100"} offset 30m

  Значения совпадут только случайно. Если оба запроса вернули
  пустой результат, значит, машина недавно перезагружалась или
  экспортёр был остановлен: ряд начинается с момента запуска.

=========================================================================
ШАГ 7. НОЛЬ ИЛИ НЕТ РЯДА: ABSENT() И ABSENT_OVER_TIME()
=========================================================================

Самое частое место ошибок в PromQL — не синтаксис, а
предположение, что «нет данных» и «ноль» — это одно и то же.
Это не так, и разница видна в каждом запросе.

ПУСТОЙ РЕЗУЛЬТАТ (нет ряда) появляется, когда ряда с таким
набором меток в базе нет вовсе. Причины: цель недоступна,
экспортёр остановлен, метрика называется иначе, метка указана
с опечаткой, ряд старше срока хранения.

ЗНАЧЕНИЕ 0 появляется, когда ряд есть и его значение равно
нулю. Причины: счётчик не рос, gauge упал до нуля, деления
не было.

Разница принципиальная. Запрос

  up{instance="10.0.2.11:9100"}

при живом экспортёре вернёт 1, при остановленном — 0.
Запрос

  up{instance="10.0.2.99:9100"}

вернёт пустоту: такой цели нет в конфигурации, и ряда для неё
не существует. Ноль и пустота — разные ответы на разные вопросы.

Проверить пустоту можно функцией absent(). Она возвращает
ряд со значением 1, если переданного ей ряда нет, и ничего
не возвращает, если ряд есть:

  absent(node_load1{instance="10.0.2.11:9100"})

Пустой результат этого запроса — хорошая новость: метрика
есть. Если же на экране появится

  {} 1

значит, ряда нет: либо машина не собирается, либо метрика
не называется node_load1.

ПОЧЕМУ ИМЕННО ТАК: absent() возвращает не «сколько отсутствует», а сам факт
  отсутствия. Поэтому у результата нет полезных меток: он состоит из
  одного ряда со значением 1 и пустым набором меток. Это неудобно и
  осознанно: функция отвечает на вопрос «есть или нет», а не «что именно
  пропало».

У absent() есть родственник для диапазонных векторов —
absent_over_time(). Он отвечает не «есть ли ряд сейчас»,
а «были ли у него точки за последние столько-то времени»:

  absent_over_time(node_load1{instance="10.0.2.11:9100"}[1h])

Если за последний час не было ни одной точки, запрос вернёт 1.
Это точнее, чем absent(): кратковременный пропуск сбора
absent() не заметит, а absent_over_time() увидит.

ЗАЧЕМ ЭТО В РАБОТЕ: absent() и absent_over_time() — основа правил оповещения
  о пропавших метриках (практика 8). Правило «метрики нет» пишется именно
  так: обычное сравнение отсутствующего ряда не сработает, потому что
  сравнивать нечего.

ВАЖНО: absent() не заменяет проверку «цель вообще есть». Если цели нет в
  конфигурации вовсе, absent() о ней ничего не знает: он смотрит на ряды,
  а не на список целей. Наличие цели проверяют по странице Targets или
  через up, а не через absent().

ПРОВЕРКА: выполните оба запроса — по существующей цели и по несуществующей:

    absent(node_load1{instance="10.0.2.11:9100"})
    absent(node_load1{instance="10.0.2.99:9100"})

  Первый вернёт пустоту, второй — ряд со значением 1.

=========================================================================
ШАГ 8. UP КАК ИНДИКАТОР СВЯЗИ
=========================================================================

Есть метрика, которая есть у каждой цели, независимо от того,
что эта цель отдаёт. Называется она up, её создаёт сам Prometheus,
и значение у неё одно из двух: 1 — последний сбор удался,
0 — не удался.

  up

Пять рядов на стенде: пять целей. Именно эта метрика отвечает
на вопрос «работает ли сбор», и именно она чаще всего попадает
в дашборды и правила оповещения.

СРАВНИМ ДВА ПОХОЖИХ ЗАПРОСА:

  up{job="node"} == 0
  absent(up{job="node"})

Первый вернёт ряды тех целей, которые существуют в конфигурации,
но не собираются: цель недоступна, экспортёр остановлен, порт
закрыт. Второй вернёт 1 только в том случае, если рядов up
с меткой job="node" нет вообще — то есть задания node в конфигурации
нет или оно ничего не обнаружило.

ЧЕСТНАЯ ОГОВОРКА, КОТОРУЮ НУЖНО ЗАПОМНИТЬ. up == 0 означает
«Prometheus не смог собрать метрики с этой цели». Это НЕ означает
«машина упала». Причины нуля по частоте:

  * остановлена или перезапускается служба node_exporter;
  * закрыт порт 9100 брандмауэром (ufw, iptables, security group);
  * экспортёр слушает не тот адрес (--web.listen-address);
  * истёк scrape_timeout: экспортёр отвечает слишком медленно;
  * кончается место на диске, и экспортёр отвечает ошибкой;
  * сама машина выключена или потеряла сеть.

Машина при этом может быть полностью работоспособной: на ней
работает сервис, отвечают пользователи, а up равен нулю, потому
что остановлен один процесс — экспортёр. И наоборот: up равен 1,
потому что экспортёр жив, а приложение на машине уже лежит.

ПОЧЕМУ ИМЕННО ТАК: up — это утверждение о связи между Prometheus и целью, а
  не о состоянии цели. Проверка идёт по pull-модели: Prometheus сам ходит
  за метриками, и up говорит только о результате этой попытки.

ЗАЧЕМ ЭТО В РАБОТЕ: из этой оговорки вырастает правило практики 8:
  оповещение по up == 0 называется «цель недоступна», а не «машина
  недоступна». Формулировка в оповещении определяет, что дежурный проверит
  первым. Если написать «сервер упал», дежурный пойдёт перезагружать
  машину, а нужно было перезапустить службу.

ПРОВЕРКА: посмотрите, что up есть даже у цели, которая ничего не отдаёт.
  Остановите экспортёр на web1 и подождите интервал сбора:

    ssh engineer@10.0.2.11 'sudo systemctl stop node_exporter'

  Через пятнадцать секунд в таблице появится ряд up{...} 0.
  Верните службу обратно:

    ssh engineer@10.0.2.11 'sudo systemctl start node_exporter'

  Вернитесь в практику 2, шаг 9, и посмотрите на страницу
  Targets: та же информация в другом виде.

=========================================================================
ШАГ 9. COUNT(UP) КАК МОСТИК К ПРАКТИКЕ 4
=========================================================================

Всё, что мы делали до этого шага, было выборкой. Формально
и count() — тоже выборка: функция не считает среднее и не
превращает счётчик в скорость, она отвечает на вопрос
«сколько рядов попало в результат». С этого запроса начинается
практика 4, и здесь он нужен как мостик.

  count(up)
  5

Одна строка без меток и значение 5: на стенде пять целей.
Заметьте, что метки при этом исчезли — агрегация всегда
что-то теряет.

Теперь посчитаем по группам, добавив by:

  count by (job) (up)
  {job="node"} 4
  {job="prometheus"} 1

by (job) означает «считать отдельно для каждого значения метки
job». Результат — два ряда, и метка job в них сохранилась.

Можно группировать по нескольким меткам сразу:

  count by (job, env) (up)
  {env="lab", job="node"} 4
  {env="lab", job="prometheus"} 1

А можно исключать метки из результата — обратная операция:

  count without (instance) (up)

ПОЧЕМУ ИМЕННО ТАК: агрегация в PromQL всегда идёт по меткам, а не по строкам
  таблицы. Формулировка «посчитать по job» на языке PromQL звучит как
  count by (job) (up): сначала выражение в скобках даёт вектор, потом
  агрегация собирает его в группы.

ЗАЧЕМ ЭТО В РАБОТЕ: count(up) — первый запрос, который пишут в новом
  мониторинге. Он отвечает на вопрос «сколько целей я вообще собираю», и с
  него начинается проверка стенда. Позже та же конструкция превращается в
  дашборд «сколько машин отдаёт метрики».

ВАЖНО: count(up) считает РЯДЫ, а не машины. Если одну и ту же машину
  собирают два задания — например, node и docker на app1, — она попадёт в
  счёт дважды, потому что это два разных ряда с разными метками job.
  Считая цели, всегда уточняйте, что именно вы считаете.

ПРОВЕРКА: сравните три запроса и объясните разницу между их результатами:

    count(up)
    count by (job) (up)
    count(up{env="lab"})

ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: Error executing query: parse error: unexpected end of input

  Синтаксис выражения не закончен. Чаще всего это незакрытая
  фигурная скобка у селектора, лишняя запятая в списке меток
  или незакрытая кавычка в значении.

    Порядок проверки. Первое — посмотрите на самый конец
    запроса: закрыты ли все скобки и кавычки.

    Второе — упростите запрос до имени метрики и добавляйте
    условия по одному, выполняя после каждого шага:

      node_load1
      node_load1{job="node"}
      node_load1{job="node",instance="10.0.2.11:9100"}

    Третье — помните, что запятых после последнего условия быть
    не должно: {job="node",} — это ошибка разбора. Так же
    ошибкой будет точка с запятой: в PromQL её нет вообще,
    многострочный запрос — всё равно одно выражение.

ПРОБЛЕМА: Error executing query: invalid expression type
  "range vector" for range query, must be Scalar or instant Vector

  Вы подали диапазонный вектор туда, где нужен мгновенный:
  в поле запроса на странице Graph или в параметр query
  мгновенного запроса API. Классический пример — node_load1[5m]
  без функции.

    Первое: проверьте, нет ли в запросе квадратных скобок
    без функции вокруг них. Скобки законны только как аргумент
    функции:

      count_over_time(node_load1[5m])
      avg_over_time(node_load1[5m])

    Второе: если диапазонный вектор действительно нужен —
    используйте endpoint range query. У него в URL есть
    параметры start, end и step:

      curl -s 'http://localhost:9090/api/v1/query_range?query=node_load1&start=2026-03-16T09:00:00Z&end=2026-03-16T10:00:00Z&step=60s'

    Третье: помните, что браузерная страница Graph сама
    выполняет запрос как range query. Именно поэтому
    node_load1 там работает, а node_load1[5m] — нет.

ПРОБЛЕМА: Error executing query: parse error: vector selector must contain
  at least one non-empty matcher

  Пустой селектор {} или селектор, у которого все условия
  пустые, например {job=~".*"}. Prometheus запрещает такие
  запросы: они выбирают всю базу.

    Первое: добавьте содержательное условие. Если нужен обзор
    метрик по имени, используйте __name__ с осмысленным
    выражением:

      {__name__=~"node_load.+"}

    Второе: если условие по метке нужно «любое значение»,
    замените его на ограничение по заданию или адресу:

      {__name__=~"node_.+",job="node"}

    Третье: проверьте регулярное выражение на предмет того,
    что оно действительно что-то ограничивает: .* и .+ ничего
    не ограничивают.

ПРОБЛЕМА: запрос верен, но таблица пуста

  Синтаксически верный запрос не находит ни одного ряда.
  Причина всегда одна из трёх: нет такого ряда, не тот момент
  времени, не та метка.

    Порядок проверки. Первое — упростите запрос до имени
    метрики без меток:

      node_load1

    Если и это пусто, метрики в базе нет: смотрите практику 2,
    шаг 4, и проверяйте, что экспортёр работает и цель UP.

    Второе — если без меток строки есть, а с метками нет,
    значит, ошибка в значении метки. Посмотрите точные
    значения в таблице без меток и сравните символ за символом:
    лишний пробел, другой регистр или адрес с другим портом
    дают пустой результат.

    Третье — проверьте диапазон времени на вкладке Graph.
    Ряд существует, но выбранный момент раньше начала сбора
    или позже остановки экспортёра. На вкладке Table момент
    берётся «сейчас»; на вкладке Graph — весь выбранный
    диапазон. Пустая таблица при непустом графике — это
    нормальная ситуация, а не ошибка.

ПРОБЛЕМА: Error executing query: vector cannot contain metrics
  with the same labelset

  Ошибка появляется, когда результат содержит два ряда с
  одинаковым набором меток. Такое бывает при операциях над
  векторами и при использовании функций, которые «схлопывают»
  метки, — например, при работе с метрикой, у которой после
  снятия метки остаётся тот же набор.

    Первое: посмотрите, что возвращает каждый операнд по
    отдельности, на вкладке Table. Строки с одинаковым набором
    меток видно сразу.

    Второе: если ошибка возникла из-за метки, которую вы
    сняли или переименовали в запросе, верните её в набор
    или добавьте различающую метку.

    Третье: на этом шаге курса такая ошибка чаще всего означает
    опечатку в имени метки: запрос обратился к метрике,
    которая есть у нескольких заданий, и после отбора осталось
    два ряда, неразличимых по меткам. Подробный разбор
    сопоставления векторов — в практике 4.

ПРОБЛЕМА: Error executing query: many-to-many matching not allowed:
  matching labels must be unique on one side

  Ошибка сопоставления векторов при арифметике или при
  соединении двух наборов данных. На этом шаге она встречается
  при попытке поделить одну метрику на другую без указания,
  по каким меткам их сопоставлять.

    Первое: убедитесь, что обе части выражения — мгновенные
    векторы: арифметика над диапазонными векторами запрещена,
    и сообщение об ошибке в этом случае будет другим.

    Второе: посмотрите на метки обеих частей на вкладке Table
    и найдите метку, которая есть только с одной стороны, —
    именно она мешает сопоставлению один к одному.

    Третье: полный разбор on, ignoring, group_left и group_right
    — в практике 4, шаг 2. До неё такие запросы лучше
    не писать наугад: результат может оказаться численно
    верным и смыслово неверным.

ПРОВЕРКА РЕЗУЛЬТАТА

Практика выполнена, если выполняются все пункты.

1. Запрос up выполняется и возвращает пять рядов с метками
   job, instance и env.

2. Вы умеете объяснить, почему node_load1[5m] в поле запроса
   даёт ошибку invalid expression type "range vector",
   а node_load1 — нет.

3. Отбор по метке работает в четырёх вариантах:

     node_filesystem_avail_bytes{mountpoint="/"}
     node_cpu_seconds_total{mode!="idle"}
     node_network_receive_bytes_total{device=~"ens.*"}
     node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}

4. Поиск по части имени метрики возвращает ожидаемые ряды:

     {__name__=~"node_load.+"}

   Три имени — node_load1, node_load5, node_load15 — на каждой
   машине.

5. offset и @ отработаны на данных стенда:

     node_load1 offset 1h
     node_load1 @ end()

6. Разница между «0» и «нет ряда» проверена руками:

     up{instance="10.0.2.11:9100"}
     up{instance="10.0.2.99:9100"}

   Первый запрос вернул значение, второй — пустоту.

7. absent() и absent_over_time() дают ожидаемый результат:
   на существующей цели пусто, на несуществующей — 1.

8. Вы можете своими словами объяснить, почему up == 0 не
   означает «машина упала», и назвать не меньше трёх причин
   нуля.

9. Мостик к следующей практике перешагнут:

     count(up)                 5
     count by (job) (up)       {job="node"} 4, {job="prometheus"} 1

10. Снимок стенда сделан перед практикой 4: дальше мы будем
    писать запросы, которые считают, и возвращаться к состоянию
    «пять целей UP» должно быть можно за минуту.
